# prospecter/core

The hexagon of the application: the domain (aggregates, value objects, repository interfaces) and the application (use cases by business intent, their ports and services). Internal Composer package of the monorepo, not published (see `docs/monorepo.md` at the repository root). Tests: `docs/core-tests.md`. Decisions: ADR 0023 (tactical DDD), 0025 (one intent per use case), 0029 (CQRS), 0030 and 0031 (bounded contexts), 0035 (plain requests and responses), 0036 (identities and moments given by the client), 0039 (rules on a set of aggregates), 0040 (`ConsultMyAccount` also tells the API who calls), 0041 and 0042 (contacts of the prospected organizations, never alone), 0042 and 0043 (domain events), 0044 (dependencies injected), 0045 (published language between contexts), 0046 (integration events), 0047 (a Contract per context), 0048 (final aggregates, nothing of the persistence), 0049 (slices after a cursor), 0071 (search by the beginning of the name or of the email), 0072 (phone numbers in E.164, libphonenumber).

## Commands

Run from the repository root (the core has its own `vendor/`, installed by `make vendor`):

- `make test-core`: the Behat scenarios (`features/`, one per intent or close: a feature may hold a sibling intent, `rattacher-a-une-holding` holds the detachment), then PHPUnit (`tests/Domain`, `tests/Application`, `tests/Architecture`)
- `make lint` / `make fix` cover the core too (PHPStan level 5, php-cs-fixer with strict types, Rector)
- one command: `docker compose run --rm --no-deps -w /var/www/src/packages/core php vendor/bin/behat features/demenager.feature`

## Layout

Grouped by bounded context, then by layer (ADR 0030); `tests/Architecture/BoundedContextsTest` fails when a context uses another one.

- `src/Accounts/{Domain,Application}`: an organization using Prospecter (`Account`) and its members (`Member`: account, person id, `Role`; signing in, with a login email, belongs to authentication outside the core); the account intents, among them `RelocateMyOrganization` (its address, the start of the routes to the organizations it prospects); `OpenAccount` opens an account with its founder, registered with every role by `RegisterTheFounder` and announced to the other contexts by the integration event `AccountOpened` (ADR 0064).
- `src/PersonalData/{Domain,Application}`: the personal data of natural persons (`Person`: account, `Purpose`, `PersonName`, job title, contact details, picture), read in clear or masked (`Masking`) by a `Reader` obtained through the port `ReaderService` (`readerFrom()`); queries `ConsultPerson`, `ConsultPersons` (batch), `SearchContacts` and `RecognizeCallingContact` (who of the contacts has a number, with the right to manage personal data), commands to change a person, and for the persons an account prospects (contacts, ADR 0041, 0042) `CollectContact` (for at least one organization, checked through the port `ProspectedOrganizations`) and `ForgetContact`, with the right to manage personal data (ADR 0031); `ForgetContactsLeftWithoutOrganization` reacts to Prospecting, `CollectTheFounderProfile` to the opening of an account (an empty profile, ADR 0064). No other context keeps personal data, only a `PersonId`.
- `src/Prospecting/{Domain,Application}`: the organizations an account prospects (`Organization`), its contacts (`PersonId`s only, `AddContact` / `RemoveContact`, never alone: `OrphanContacts`), `StopProspecting`, the `Prospector` who acts (with or without the right to manage personal data), read through the port `ProspectorService` (`prospectorFrom()`, implemented outside the core from the members of Accounts), the port `KnownContacts` (whether a person is one the account prospects, answered from PersonalData); `ConsultOrganizationsOfContacts` (batch), `RecognizeCallingOrganization` (which organization has a number).
- `src/SharedKernel/{Domain,Application}`: what every context shares, kept small: the published identities `AccountId`, `MemberId`, `PersonId` and `OrganizationId`, in `Domain/Event` the bases of every domain event (`DomainEvent`, `OrganizationEvent`, `PersonEvent`, `AccountEvent`), `ReleasesEvents` and `RecordsEvents`, `Email` (in lower case), `PhoneNumber` (E.164, ADR 0072), `ContactDetails`, `LegalIdentity`, `Address` and its `GeoPoint`, `File`, `Slice` (a list newest first and the cursor of what follows, ADR 0049), `SearchKey` and `SearchKeys` (an aggregate is found by the beginning of its name or of its email, without accents, case, spaces nor punctuation, ADR 0071), `Uuid`, the business exceptions in `Domain/Exception` (`BusinessException`, `NotFound`, `BusinessRuleViolation` naming the faulty field, `NotPossibleInItsState`, `NotAllowed`), and in the application `CommandHandler`, `QueryHandler`, `EventHandler`, `PublishesEvents`, `RefusalTranslatingHandler`, the port `Events`, `UseCaseRefused` and its `ErrorType`, `FileResponse`, the port `Storage` and `FileStore`, the port `GeoLocation` and `GeoLocalizer`. Each context keeps its own exceptions in `Domain/Exception` (`UnknownOrganization`...).
- `<Context>/Application/<Intent>/`: one package per use case, CQRS (ADR 0029). A command (`Relocate/Relocate`, readonly data) and its handler (`RelocateHandler`, implements `CommandHandler`, `__invoke(Relocate): void`) change the state and return nothing. A query (`ConsultOrganization/ConsultOrganization`) and its handler return a response; only queries return data. What the intents of a context share stays one level up (`OrganizationResponse::of()`, `FileResponse`).

## Rules

- Pure PHP: `composer.json` requires only `php`, `ext-intl` (the normalization of `SearchKey`) and `giggsey/libphonenumber-for-php` (what a phone number is, `PhoneNumber`, ADR 0072), dev tools aside. Never add a framework or infrastructure dependency; the outside is reached through ports (`Port/`, repository interfaces) implemented in `apps/api`.
- Names: the interface says the role, the implementation its technology (`OrganizationRepository`, `DynamoOrganizationRepository`, `InMemoryOrganizationRepository`). No `Impl`, no `Interface` suffix, no CRUD verbs in use cases (`Create`, `Get`, `Update`, `Delete`).
- A command handler is one intent: it loads the acting member or prospector (the command carries its id as a string) and the aggregate of its intent, calls its intention methods with `by: $user` (`StartProspecting` places and describes the new organization), saves it with `save()`, and returns nothing; a query handler only reads. It changes only the data of its intent, and is reused by another client or a data recovery, never by another use case. No transaction: one aggregate per use case; what other aggregates or contexts must do follows from the events it recorded (ADR 0042).
- Business rules live in the aggregates: named constructors (`Organization::prospectedBy`, `Account::open`, `Member::register`), intention methods (`relocateTo`, `removeLogo`), no setters; an invariant is checked before the change. Aggregates reference each other by identity, never by object.
- The client gives the identity of what it creates (a UUID v7 string in the command) and the moment of every command (`executedAt`); the intention methods take it (`at:`) and the aggregates keep `createdAt` and `modifiedAt` (ADR 0036). A rule on a set of aggregates, out of reach of one of them, is a domain service of the hexagon (ADR 0039): `EmailUniqueness` keeps an email unique among the persons of an account for a purpose (PersonalData), among the organizations of an account (Prospecting); it asks the repository (`isEmailUsed()`), and the handler calls it before `save()`. Repositories and doubles answer questions, they never decide.
- The domain never crosses the application (ADR 0035): requests are flat data (strings, numbers, `\DateTimeImmutable`, `\SplFileInfo`), responses the same plus data structures of the application, built by named constructors (`OrganizationResponse::of()`), intentions by name; `tests/Architecture/ApplicationBoundaryTest` fails otherwise. A handler builds the value objects and implements `CommandHandler`, `QueryHandler` or `EventHandler`, without error handling: clients call it through the decorator `RefusalTranslatingHandler`, which translates a `BusinessException` into `UseCaseRefused::because()` (type, message of the domain, field, the domain exception as previous); infrastructure exceptions go through. Exceptions get named constructors (`UnknownOrganization::identifiedBy()`, `BusinessRuleViolation::because()`). Value objects are `final readonly`. Aggregates hold their value objects as they are (`private ?Address $address`): the domain knows nothing of persistence, the API mapping adapts to it (ADR 0028). A new property of an aggregate or of a value object requires a change of its document in the API (`apps/api/src/<Context>/Persistence/*Document.php`, ADR 0048). A class of a domain is `final`, unless the domain extends it (`tests/Architecture/DomainClassesAreFinalTest`). A list is sliced, never counted: the repositories answer a `Slice` after a cursor, and search by the `searchKeys()` of the aggregate.
- Authentication and roles are not the business of the core: the delivery authenticates and checks roles, a request carries the id of the acting user. The aggregate decides the rest (ADR 0026): an organization is managed by the prospectors of the account prospecting it, anybody else gets `UnknownOrganization` (not found); an account by its members.
- An aggregate offers its possible intents (`Organization::possibleIntentsOf($prospector)`, `Account::possibleIntentsOf($member)`, `Person::possibleIntentsOf($reader)`), which the API turns into links (ADR 0027); every intention method starts with the same check (`ensurePossible`) and throws `NotPossibleInItsState` for what is not offered. A new intention gets a case in the intent enum, a check, and a line in `OrganizationIntentsTest`, `AccountIntentsTest` or `PersonIntentsTest`.
- Domain events (ADR 0042, 0043): every intention method records one event in the past tense (`recordThat(new Relocated(...))`), with identities only, never personal data; an aggregate `implements ReleasesEvents` and `use RecordsEvents`. Its events live in `<Context>/Domain/Event`, and never leave the context. The handler `use PublishesEvents` and calls `publishWhatHappenedTo($aggregate)` after saving it: the events go on the port `Events`, delivered synchronously, within the use case. A new intention gets its event, and its intents test checks it is recorded. What another context must know is an integration event (ADR 0046): plain data in `<Context>/Contract/Event` (`ContactCollected`, `ContactForgotten` of PersonalData, `ContactsLeftWithoutOrganization` of Prospecting), built from the domain event and published by a handler of the emitting context (`PublishContactCollectedHandler`). The other context reacts with an `EventHandler` (`__invoke(TheIntegrationEvent)`), translating it into its words, as the member who did the gesture, through the intention methods: no rights bypassed. Only integration events cross contexts (`tests/Architecture/BoundedContextsTest`). A Contract (`<Context>/Contract/{Service,Event}`, ADR 0047) is plain data importing nothing (`tests/Architecture/ContractTest`): what a context promises the others, the contract package of the context deployed apart. A contact is never alone: it is collected for at least one organization, and a contact no organization names any more is erased.
- Services (`FileStore`, `GeoLocalizer`, `EmailUniqueness`, `OrphanContacts`) and the decorator `RefusalTranslatingHandler` are real classes of the hexagon, never doubled. They are injected into the handlers, never built by them (ADR 0044): a constructor builds nothing, a service is built by the client (the container of the API, `tests/Acceptance/Application` in the scenarios); `make lint` fails otherwise (`tools/phpstan/DependenciesAreInjectedRule`).
- A context never uses another one: it declares a port in its own words (`ProspectorService`, `ReaderService`, `KnownContacts`, `ProspectedOrganizations`), implemented outside the core by an anticorruption adapter (`App\Prospecting\AccountsProspectorService`, `App\PersonalData\AccountsReaderService`, `App\Prospecting\PersonalDataKnownContacts`, `App\PersonalData\ProspectingOrganizations`), doubled in the scenarios by the same code (`tests/Double`). The adapter sees of the other context only what it publishes (ADR 0045): the queries of its `Contract/Service` (`ConsultMember`, `IsAContactOf`, `IsProspectedBy`, their handlers being use cases of its `Application`), answering plain data with only what the others need, checking no caller, fixed by `features/langage-publie.feature`; `tests/Architecture/BoundedContextsTest` fails otherwise. A new question between contexts is a new published query, its scenario, and the rule it answers in the aggregate (`Person::isAContactOf()`).
- The API sends commands on a synchronous Symfony Messenger bus (every `CommandHandler` is registered on it through `RefusalTranslatingHandler`) and receives the query handlers already wrapped in the same decorator, by the name of their intent (`RefusalTranslatingHandler $consultOrganization`); it builds commands with named arguments: renaming a property breaks it (PHPStan and the API tests catch it), so change the core and the API in the same commit.
- The core knows no bus: `tests/Acceptance/Application` sends a command to its handler (found by the type of `__invoke()`, as Messenger does), through `RefusalTranslatingHandler` like the API, and is the only place that knows how a handler is called.
- Clean code (`docs/clean-code.md`): names instead of explanatory comments, docblocks only for generics and array shapes.
