# prospecter/core

The hexagon of the application: the domain (aggregates, value objects, repository interfaces) and the application (use cases by business intent, their ports and services). Internal Composer package of the monorepo, not published (see `docs/monorepo.md` at the repository root). Tests: `docs/core-tests.md`. Decisions: ADR 0023 (tactical DDD), 0025 (one intent per use case), 0029 (CQRS), 0030 and 0031 (bounded contexts), 0035 (plain requests and responses), 0036 (identities and moments given by the client), 0039 (rules on a set of aggregates), 0040 (`ConsultMyAccount` also tells the API who calls), 0041 and 0042 (contacts of the prospected organizations, never alone), 0042 and 0043 (domain events).

## Commands

Run from the repository root (the core has its own `vendor/`, installed by `make vendor`):

- `make test-core`: the Behat scenarios (`features/`, one per intent or close: a feature may hold a sibling intent, `rattacher-a-une-holding` holds the detachment), then PHPUnit (`tests/Domain`, `tests/Application`, `tests/Architecture`)
- `make lint` / `make fix` cover the core too (PHPStan level 5, php-cs-fixer with strict types, Rector)
- one command: `docker compose run --rm --no-deps -w /var/www/src/packages/core php vendor/bin/behat features/demenager.feature`

## Layout

Grouped by bounded context, then by layer (ADR 0030); `tests/Architecture/BoundedContextsTest` fails when a context uses another one.

- `src/Accounts/{Domain,Application}`: an organization using Prospecter (`Account`) and its members (`Member`: account, person id, `Role`; signing in, with a login email, belongs to authentication outside the core); the account intents.
- `src/PersonalData/{Domain,Application}`: the personal data of natural persons (`Person`: account, `Purpose`, `PersonName`, job title, contact details, picture), read in clear or masked (`Masking`) by a `Reader` obtained through the port `Readers`; queries `ConsultPerson`, `ConsultPersons` (batch) and `SearchContacts`, commands to change a person, and for the persons an account prospects (contacts, ADR 0041, 0042) `CollectContact` (for at least one organization, checked through the port `ProspectedOrganizations`) and `ForgetContact`, with the right to manage personal data (ADR 0031); `ForgetContactsLeftWithoutOrganization` reacts to Prospecting. No other context keeps personal data, only a `PersonId`.
- `src/Prospecting/{Domain,Application}`: the organizations an account prospects (`Organization`, `OrganizationId`, `Address`, `GeoPoint`), its contacts (`PersonId`s only, `AddContact` / `RemoveContact`, never alone: `OrphanContacts`), `StopProspecting`, the `Prospector` who acts (with or without the right to manage personal data), read through the port `Prospectors` (implemented outside the core from the members of Accounts), the port `KnownContacts` (whether a person is one the account prospects, answered from PersonalData), the port `GeoLocation`; `ConsultOrganizationsOfContacts` (batch).
- `src/SharedKernel/{Domain,Application}`: what every context shares, kept small: the published identities `AccountId`, `MemberId`, `PersonId` and `OrganizationId`, in `Domain/Event` the bases of every domain event (`DomainEvent`, `OrganizationEvent`, `PersonEvent`, `AccountEvent`) and the events of the published language (`ContactCollected`, `ContactsLeftWithoutOrganization`, `ContactForgotten`), `ReleasesEvents` and `RecordsEvents`, `Email`, `ContactDetails`, `LegalIdentity`, `File`, `Page`, `Uuid`, the business exceptions in `Domain/Exception` (`BusinessException`, `NotFound`, `BusinessRuleViolation` naming the faulty field, `NotPossibleInItsState`, `NotAllowed`), and in the application `CommandHandler`, `QueryHandler`, `EventHandler`, `PublishesEvents`, `RefusalTranslatingHandler`, the port `Events`, `UseCaseRefused` and its `ErrorType`, `FileResponse`, the port `Storage` and `FileStore`. Each context keeps its own exceptions in `Domain/Exception` (`UnknownOrganization`...).
- `<Context>/Application/<Intent>/`: one package per use case, CQRS (ADR 0029). A command (`Relocate/Relocate`, readonly data) and its handler (`RelocateHandler`, implements `CommandHandler`, `__invoke(Relocate): void`) change the state and return nothing. A query (`ConsultOrganization/ConsultOrganization`) and its handler return a response; only queries return data. What the intents of a context share stays one level up (`OrganizationResponse::of()`, `FileResponse`).

## Rules

- Pure PHP: `composer.json` requires only `php` (dev tools aside). Never add a framework or infrastructure dependency; the outside is reached through ports (`Port/`, repository interfaces) implemented in `apps/api`.
- Names: the interface says the role, the implementation its technology (`OrganizationRepository`, `DoctrineOrganizationRepository`, `InMemoryOrganizationRepository`). No `Impl`, no `Interface` suffix, no CRUD verbs in use cases (`Create`, `Get`, `Update`, `Delete`).
- A command handler is one intent: it loads the acting member or prospector (the command carries its id as a string) and the aggregate of its intent, calls its intention methods with `by: $user` (`StartProspecting` places and describes the new organization), saves it with `save()`, and returns nothing; a query handler only reads. It changes only the data of its intent, and is reused by another client or a data recovery, never by another use case. No transaction: one aggregate per use case; what other aggregates or contexts must do follows from the events it recorded (ADR 0042).
- Business rules live in the aggregates: named constructors (`Organization::prospectedBy`, `Account::open`, `Member::register`), intention methods (`relocateTo`, `removeLogo`), no setters; an invariant is checked before the change. Aggregates reference each other by identity, never by object.
- The client gives the identity of what it creates (a UUID v7 string in the command) and the moment of every command (`executedAt`); the intention methods take it (`at:`) and the aggregates keep `createdAt` and `modifiedAt` (ADR 0036). A rule on a set of aggregates, out of reach of one of them, is a domain service of the hexagon (ADR 0039): `EmailUniqueness` keeps an email unique among the persons of an account for a purpose (PersonalData), among the organizations of an account (Prospecting); it asks the repository (`isEmailUsed()`), and the handler calls it before `save()`. Repositories and doubles answer questions, they never decide.
- The domain never crosses the application (ADR 0035): requests are flat data (strings, numbers, `\DateTimeImmutable`, `\SplFileInfo`), responses the same plus data structures of the application, built by named constructors (`OrganizationResponse::of()`), intentions by name; `tests/Architecture/ApplicationBoundaryTest` fails otherwise. A handler builds the value objects and implements `CommandHandler` or `QueryHandler`, without error handling: clients call it through the decorator `RefusalTranslatingHandler`, which translates a `BusinessException` into `UseCaseRefused::because()` (type, message of the domain, field, the domain exception as previous); infrastructure exceptions go through. Exceptions get named constructors (`UnknownOrganization::identifiedBy()`, `BusinessRuleViolation::because()`). Value objects are `final readonly`. Aggregates hold their value objects as they are (`private ?Address $address`): the domain knows nothing of persistence, the API mapping adapts to it (ADR 0028). A new property of an aggregate or of a value object requires a change of `apps/api/config/doctrine/`.
- Authentication and roles are not the business of the core: the delivery authenticates and checks roles, a request carries the id of the acting user. The aggregate decides the rest (ADR 0026): an organization is managed by the prospectors of the account prospecting it, anybody else gets `UnknownOrganization` (not found); an account by its members.
- An aggregate offers its possible intents (`Organization::possibleIntentsOf($prospector)`, `Account::possibleIntentsOf($member)`, `Person::possibleIntentsOf($reader)`), which the API turns into links (ADR 0027); every intention method starts with the same check (`ensurePossible`) and throws `NotPossibleInItsState` for what is not offered. A new intention gets a case in the intent enum, a check, and a line in `OrganizationIntentsTest`, `AccountIntentsTest` or `PersonIntentsTest`.
- Domain events (ADR 0042, 0043): every intention method records one event in the past tense (`recordThat(new Relocated(...))`), with identities only, never personal data; an aggregate `implements ReleasesEvents` and `use RecordsEvents`. Its events live in `<Context>/Domain/Event`, only those another context handles in `SharedKernel/Domain/Event`. The handler `use PublishesEvents` and calls `publishWhatHappenedTo($aggregate)` after saving it: the events go on the port `Events`, delivered synchronously, within the use case. A new intention gets its event, and its intents test checks it is recorded. Another context reacts with an `EventHandler` (`__invoke(TheEvent)`), as the member who did the gesture, through the intention methods: no rights bypassed. Only the events of `SharedKernel\Domain\Event` cross contexts. A contact is never alone: it is collected for at least one organization, and a contact no organization names any more is erased.
- Services (`FileStore`, `GeoLocalizer`, `EmailUniqueness`, `OrphanContacts`) and the decorator `RefusalTranslatingHandler` are real classes of the hexagon, built by the handlers or the client, never doubled.
- A context never uses another one: it declares a port in its own words (`Prospectors`, `Readers`, `KnownContacts`, `ProspectedOrganizations`), implemented outside the core by an anticorruption adapter (`App\Prospecting\AccountsProspectors`, `App\PersonalData\AccountsReaders`, `App\Prospecting\PersonalDataKnownContacts`, `App\PersonalData\ProspectingOrganizations`), and doubled in the scenarios (`MembersAsProspectors`, `MembersAsReaders`, `PersonsAsKnownContacts`, `OrganizationsAsProspectedOrganizations`).
- The API sends commands on a synchronous Symfony Messenger bus (every `CommandHandler` is registered on it through `RefusalTranslatingHandler`) and calls the query handlers directly, through the same decorator; it builds commands with named arguments: renaming a property breaks it (PHPStan and the API tests catch it), so change the core and the API in the same commit.
- The core knows no bus: `tests/Acceptance/Application` sends a command to its handler (found by the type of `__invoke()`, as Messenger does), through `RefusalTranslatingHandler` like the API, and is the only place that knows how a handler is called.
- Clean code (`docs/clean-code.md`): names instead of explanatory comments, docblocks only for generics and array shapes.
