# Authentication

The API (`apps/api`) is an OAuth 2 authorization server and resource server; the SPA (`apps/front`) is a public client using the authorization code flow with PKCE, as recommended by OAuth 2.1 for browser applications.

```
SPA (local.prospecter.io)                 API (api.local.prospecter.io)
 1. GET /authorize?client_id=prospecter-front&code_challenge=…  ─────▶  not signed in → 302 /login
 2.                                             user signs in on /login (session cookie, src/Auth)    
 3.                                             ◀───── 302 /auth/callback?code=…&state=…
 4. POST /token (code + code_verifier) ───────────────────────▶  access token (JWT, 15 min) + refresh token (30 days)
 5. GET /api/me  Authorization: Bearer <access token> ────────▶  stateless check of the JWT signature
 6. before expiry: POST /token grant_type=refresh_token ──────▶  new pair, the old refresh token is revoked
```

## API side

- `league/oauth2-server-bundle`, configured in `config/packages/league_oauth2_server.yaml`: authorization code and refresh token grants only (password and implicit disabled), PKCE required for public clients, scope `api`.
- The client `prospecter-front` (public, redirect URI `FRONT_URL/auth/callback`) is created by `DataFixtures/OAuthClientFixtures`, so `make db` always recreates it.
- Keys: `config/jwt/private.pem` / `public.pem`, generated by `make keys`, never committed. `OAUTH_PASSPHRASE` and `OAUTH_ENCRYPTION_KEY` in `.env` are development values: override them in production.
- Sign-in page: `Controller/Auth/Login` + `Security/ProspecterAuthenticator` (password checked by `Auth\Passwords`, CSRF protected), firewall `main` with a session. After sign-in it resumes the pending `/authorize`.
- Consent is auto-approved for this first-party client (`EventListener/AuthorizationRequestListener`).
- Resource server: firewall `api` (`^/api/`), stateless, `oauth2: true`. The token subject is the user name; `ProspecterUserProvider` loads the user through `UserRepository::ofUserName()`. Missing or invalid token: 401 `application/problem+json` with `WWW-Authenticate: Bearer`.
- Logout: `/logout` ends the API session and redirects to `FRONT_URL` (`EventListener/LogoutListener`).
- CORS (`nelmio_cors.yaml`): the SPA origin may call `/api/` and `/token` with the `Authorization` header.

## Credentials, outside the hexagon

Signing in is infrastructure, not a business rule: the use cases receive an already authenticated user (`UseCaseConsumer`) and only decide what this user may do. The core therefore knows no password.

- `apps/api/src/Auth`: `Credentials` (Doctrine entity, table `credentials`: the user id and the password hash) and `Passwords` (set, verify, upgrade an outdated hash at sign-in). The hashing algorithm is `auto` (`security.yaml`, cheaper settings in tests).
- `PATCH /api/me/password` sets it (204). Changing one's user name (`PATCH /api/me/user-name`) invalidates the token subject: the SPA signs in again. `bin/console app:user:set-password <userName>` sets it by hand; the fixtures give `prospector` the password `password`.
- The module depends on the core only through the user id and user name, so that it can become a dedicated authorization server later.

## SPA side

- `src/app/auth.ts`: `oidc-client-ts` with explicit endpoints (the API is plain OAuth 2, not OpenID Connect: no discovery document, no id token, no user info), `automaticSilentRenew` with the refresh token.
- Tokens are kept in `sessionStorage`: per tab, gone when the tab closes, readable by scripts of the page. The alternatives were memory only (sign in again on every reload) or a backend-for-frontend holding the tokens in an HttpOnly cookie (more infrastructure). Keep the Content Security Policy strict in production.
- `routes/_app.tsx` guards every page with the stored session and sends anonymous users through the flow, then back to the page they asked for (`state.returnTo`).
- `shared/api/client.ts` adds the bearer token and retries once after a refresh on 401.
- Changing the user name in "Mon compte" invalidates the token subject: the SPA signs the user out and in again.

## Tests

- API: `tests/Api/OAuthFlowTest` runs the real flow (authorize with PKCE, token, refresh rotation, refusal without PKCE, 401 format); every API test signs in through it (`Base/ApiTestCase::login()`).
- Front: `e2e/journey.spec.ts` signs in through the real sign-in page.
