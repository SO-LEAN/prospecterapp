# Authentication

The authorization server is its own app, `apps/auth` (ADR 0034): it signs members in and issues the OAuth 2 tokens. The API (`apps/api`) is a resource server only: it checks the access tokens with the public key of the authorization server. The SPA (`apps/front`) is a public client using the authorization code flow with PKCE, as recommended by OAuth 2.1 for browser applications.

Both apps share the host `api.local.prospecter.io`: nginx sends `/authorize`, `/token`, `/login`, `/logout` and `/auth/*` to `apps/auth`, the rest to `apps/api` (`docker/nginx/templates/api.conf.template`).

```
SPA (local.prospecter.io)                         auth (api.local.prospecter.io, apps/auth)
 1. GET /authorize?client_id=prospecter-front&code_challenge=…  ─────▶  not signed in: kept in the session,
                                                                   302 to the SPA /auth/sign-in
 2. POST /login {email, password}, Origin of the SPA, cookie ─▶  session cookie (HttpOnly, Secure, Lax),
                                                                   200 {resume: the interrupted /authorize}
 3. GET <resume> ──────────────────────────────────────────────▶  302 /auth/callback?code=…&state=…
 4. POST /token (code + code_verifier) ───────────────────────▶  access token (JWT, 15 min, subject = member id)
                                                                   + refresh token (30 days)
                                                  API (api.local.prospecter.io, apps/api)
 5. GET /api/me  Authorization: Bearer <access token> ────────▶  JWT signature, expiry and client checked
                                                                   with the public key, member loaded by its id
 6. before expiry: POST /token grant_type=refresh_token ──────▶  (auth) new pair, the old refresh token revoked
```

## Authorization server: `apps/auth`

- `league/oauth2-server-bundle` (`config/packages/league_oauth2_server.yaml`): authorization code and refresh token grants only, every other grant disabled explicitly (client credentials is on by default in the bundle); the only client, `prospecter-front`, is allowed exactly these two; PKCE required for public clients, scope `api`.
- The client `prospecter-front` (public, redirect URI `FRONT_URL/auth/callback`) is created by `DataFixtures/OAuthClientFixtures`, so `make db` always recreates it.
- Keys: `config/jwt/private.pem` / `public.pem`, generated by `make keys`, never committed. `OAUTH_PASSPHRASE` and `OAUTH_ENCRYPTION_KEY` in `.env` are development values: override them in production.
- What a member signs in with: `Credentials` (table `credentials`: the member id, the login email, unique on the platform, the password hash), `LoginEmails`, `Passwords` (hashing `auto`, outdated hashes upgraded at sign-in). The login email is an access identifier, not the contact email of the profile kept by PersonalData (ADR 0032). The app knows the member by its id only, never the core.
- Sign-in (ADR 0037): the screen is in the SPA; `POST /login` (JSON, documented by `Controller/SignIn`) is handled by `Security/SignInAuthenticator`, firewall `main` with a session. It accepts the SPA origin only (`Origin` = `FRONT_URL`, against login CSRF; CORS with credentials on `^/login$`), answers 401 for a wrong login email or password alike, 429 after 5 failures in a minute (`login_throttling`, per address and login email), and 200 with `resume`, the `/authorize` it interrupted (null when none was). As the entry point of `/authorize`, it sends an anonymous request to `FRONT_URL/auth/sign-in`. Consent is auto-approved for this first-party client (`EventListener/AuthorizationRequestListener`); `/logout` redirects to `FRONT_URL`.
- The subject of the access token is the member id (`Security/SignedInMember`): changing the login email does not invalidate it.
- `GET /auth/me`, `PATCH /auth/me/login-email` (422 when another member signs in with it), `PATCH /auth/me/password` (204): what I sign in with, with an access token of my own (firewall `me`, resource server of the bundle). Contract: `apps/auth/openapi.json`, front types `src/shared/api/auth-schema.d.ts`.
- `bin/console app:user:set-password <login email>` sets a password by hand; the fixtures sign `prospector@solean-it.io` and `assistant@solean-it.io` in with `password`, under the member ids the API fixtures give them.

## Resource server: `apps/api`

- Firewall `api` (`^/api/`, stateless) with Symfony's `access_token` authenticator: `Security\AccessTokenHandler` checks the JWT (RS256 signature with `AUTH_PUBLIC_KEY`, expiry, audience `AUTH_CLIENT_ID`) without calling the authorization server; `Security\MemberProvider` reads the member named by the subject, its identities and roles, with the query `ConsultMyAccount` (ADR 0040). Missing or invalid token: 401 `application/problem+json` with `WWW-Authenticate: Bearer`.
- A token stays valid until it expires (15 min) even if its refresh token is revoked: the price of not calling the authorization server on every request.
- Roles are checked by `#[IsGranted]` (403 problem+json from `Security\ApiAccessDeniedHandler`), and the aggregate decides whether this member may change something (ADR 0026). The core knows no password.

## SPA side

- `src/shared/auth/user-manager.ts`: `oidc-client-ts` with explicit endpoints (plain OAuth 2, not OpenID Connect: no discovery document, no id token, no user info), `automaticSilentRenew` with the refresh token.
- Tokens are kept in `sessionStorage`: per tab, gone when the tab closes, readable by scripts of the page. The alternatives were memory only (sign in again on every reload) or a backend-for-frontend holding the tokens in an HttpOnly cookie (more infrastructure). Keep the Content Security Policy strict in production.
- `routes/_app.tsx` guards every page with the stored session and sends anonymous users through the flow, then back to the page they asked for (`state.returnTo`).
- `routes/auth/sign-in.tsx` is the sign-in screen (`features/sign-in`): it posts the credentials with `signInApi` (cookie included, no token), then opens `resume` again, or starts the flow when the screen was opened directly. A member already signed in on the authorization server goes through `/authorize` without seeing it.
- `shared/api/client.ts`: `api` for the API, `authApi` for `/auth/me`; both add the bearer token and retry once after a refresh on 401. `signInApi` sends the credentials only.

## Tests

- Auth: `tests/OAuthFlowTest` runs the real flow (authorize with PKCE, token whose subject is the member id, refresh rotation, refusal without PKCE, 401 format); `tests/MeTest`, `tests/SignInTest` (resume, wrong credentials, other origin, throttling).
- API: `tests/Api/AccessTokenTest` (expired, other client, forged, unknown member); every API test signs its own tokens with a key pair made by `tests/bootstrap.php` in `var/test-jwt` (`Base/ApiTestCase::login()`).
- Front: `features/sign-in/components/sign-in-form.test.tsx`; `e2e/journey.spec.ts` signs in through the real sign-in screen.
