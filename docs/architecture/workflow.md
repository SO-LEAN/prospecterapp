# The workflow

What is in force; the reasons are in the records it names (`docs/adr`), read only to know why or before changing it (ADR 0090).

## Branches, pull requests, CI

- `dev` integrates the work (ADR 0057): a `feature/<name>` or `fix/<name>` branch starts from `dev` and comes back by pull request (`gh pr create --base dev`), merged by rebase once the CI passes (`gh pr merge --rebase`): `dev` stays linear. `dev` goes to `main` by a pull request merged by a merge commit (`gh pr merge --merge`, ADR 0058: a rebase merge of GitHub rewrites the commits, `main` and `dev` would diverge). A `hotfix/<name>` starts from `main`, comes back to `main` the same way, then is cherry-picked onto `dev` (a `fix/` branch).
- `dev` is the default branch of the repository (pull requests and clones start there). `main` and `dev` are protected (rulesets `dev` and `main`, no bypass): no direct push, the check `ci` must pass, no force-push; rebase only on `dev`, merge commits only on `main`.
- The CI (`.github/workflows/ci.yml`) runs on the pull requests to `dev` and `main` and on the pushes of `dev` and `main`, not on the pushes of the branches of work (ADR 0109): run `make ci` before pushing. A pull request runs the checks its changes need (ADR 0110, `make changed-checks`, `make/changed-checks.sh`: a project when its files change, the API and the contract when the core does, the contract when the API or the front does, every check when a Makefile, an image of the command line, `docker-compose.yml` or the workflow does, none but the secrets for the documentation, the journeys when the core, an app or an image of the stack does), a push of `dev` or `main` every one; each in a job of its own, together (`make check-secrets`, `check-infra`, `check-core`, `check-api`, `check-storage`, `check-front`, `check-contract`, `check-e2e`), whose steps `make -j` runs together too (the PHPStan, the php-cs-fixer and the Rector of a PHP project beside its tests; the lint of the front beside its tests, its build after them); the job `ci` sums them up, the check the rulesets require. The journeys are a check too (`check-e2e`, ADR 0116), needed by a change of the core, the apps or the images of the stack: the job starts the stack on the runner, recreates its data and runs `make e2e`, its report kept a week when it fails (the artifact `playwright-report`); `check-e2e` refuses to run in the main checkout, whose data it would recreate. `make ci` runs the checks of the changes since `origin/dev`, committed or not (`ALL=1` every one): it builds the images, installs the dependencies and checks the contract when it is needed, then runs the others together, each printing its output once it ends; it needs no stack, the tests of the API and the storage running on the MiniStack of the tests of the checkout, and the lint of the Terraform keeps what it downloads in `.cache/`. Locally, it leaves the journeys to the integration: `make e2e` runs them on the stack of the checkout. A pull request touching `apps/*/infra` is also planned by Terraform (`.github/workflows/terraform-plan.yml`, ADR 0060), a comment per app and instance; once merged into `dev`, it is applied to the instance `dev` (`.github/workflows/terraform-apply-dev.yml`, ADR 0061), and once in `main`, to `prod` after an approval in the environment `production` (`.github/workflows/terraform-apply-prod.yml`, ADR 0062); both can be run by hand on their branch (`workflow_dispatch`), every app applied: after the edge changed (ADR 0067), or for the second apply of a new instance (ADR 0069).
- A pull request merged into `dev` moves the tickets it refers to (`Refs <backlog>#<n>`) to the column QA of the project of the backlog (`.github/workflows/backlog-qa.yml`); the release to `main` and a pull request closed without merge leave the board alone. The repository needs the secret `PROJECT_TOKEN` (a fine-grained token: Projects of the organization read and write, Issues of the backlog read) and the variables `BACKLOG_OWNER`, `BACKLOG_PROJECT` (its number) and `BACKLOG_REPOSITORY` (`<owner>/<repository>`).
- Conventional commits (`feat:`, `fix:`, `refactor:`, `chore:`, `docs:`) explaining why.
