# The workflow

This document states the rules in force. The decision records (`docs/adr`) explain why: read them only for that, or before changing a rule (ADR 0090).

## Branches, pull requests, CI

- `dev` integrates the work (ADR 0057). A `feature/<name>` or `fix/<name>` branch starts from `dev` and comes back through a pull request (`gh pr create --base dev`). A pull request to `dev` is merged through GitHub's merge queue (ADR 0220): the maintainer adds it to the queue once its CI passes, and the queue rebases it onto `dev` and onto the pull requests queued before it, runs the CI on that result, then merges it by rebase. So `dev` stays linear, and nobody brings a pull request up to date with `dev` by hand. `dev` goes to `main` through a pull request merged with a merge commit (`gh pr merge --merge`, ADR 0058). GitHub's rebase merge rewrites the commits, so `main` and `dev` would diverge. A `hotfix/<name>` branch starts from `main` and comes back to `main` the same way. It is then cherry-picked onto `dev`, as a `fix/` branch.
- `dev` is the repository's default branch (pull requests and clones start there). `main` and `dev` are protected by the rulesets `dev` and `main`, with no bypass. They refuse direct pushes and force-pushes, and the `ci` check must pass. `dev` takes only rebase merges, through its merge queue, which also requires the `e2e` check; its branches need not be up to date with `dev`. `main` takes only merge commits, without a queue.
- The CI (`.github/workflows/ci.yml`) runs on pull requests to `dev` and `main`, in `dev`'s merge queue (the event `merge_group`) and on pushes to `dev` and `main`, not on pushes to work branches (ADR 0109). Run `make ci` before pushing.
  - A pull request runs the checks its changes need (ADR 0110, `make changed-checks`, `make/changed-checks.sh`):
    - a project's checks when its files change;
    - the API and the contract when the core changes;
    - the contract when the API or the front changes;
    - the walls of the event storming when the core, the API, their generator or the walls change (`make check-event-storming`: every wall written again, and the files that differ from the committed ones named);
    - every check when a Makefile, a command-line image, `docker-compose.yml` or the workflow changes;
    - only the secrets check for documentation;
    - the journeys when the core, an app or a stack image changes, run by the merge queue only (the job `e2e`), never by a pull request's CI, a push or `make ci`.

    The merge queue runs the checks the changes of its group need since the `dev` it starts from, the journeys among them. A push to `dev` or `main` runs every check but the journeys.
  - A pull request's `check-api` leaves out the API tests that re-test a core rule (the `core-rule` group, ADR 0204), and so does the merge queue. A push to `dev` or `main` runs them (`ALL=1`): a test of the group that fails makes that push's CI red. Locally, `make ci ALL=1` runs every check with the group.
  - Each check runs in its own job, all of them in parallel (`make check-secrets`, `check-infra`, `check-core`, `check-api`, `check-storage`, `check-front`, `check-contract`, `check-event-storming`, `check-e2e`). `make -j` also runs each check's steps in parallel: a PHP project's PHPStan, php-cs-fixer and Rector beside its tests; the front's lint beside its tests, its build after them. Their output is not synchronised (no `--output-sync`, which holds a command's output until it ends), so the tests' progress shows while they run. The `ci` job sums them up. It is the check that the rulesets require.
  - The API's check is split into four jobs (ADR 0221). `api-lint` runs its lint (`make check-api-lint`). Each `api-tests-<i>-of-3` runs one share of its test files, dealt in turn, in four processes (`make check-api-tests-<i>-of-3`, `paratest --shard`). The workflow sets the number of shares once (`API_TEST_JOBS`), and the `changes` job expands the check `api` into these jobs. The `ci` job passes only when all of them pass. `make check-api` and `make ci` still run the lint and the tests together.
  - The CI keeps caches between its runs:
    - the Composer and pnpm dependencies, keyed by their lock files;
    - the PHP and Node images, each as an archive keyed by the tag make expects of it (`make images-env`). A job loads the archive (`make image-load`, `docker load`). When the cache does not hold the tag yet, after a change of the image's `docker/` directory, the job builds the image and saves its archive;
    - the PHP lint's caches (PHPStan, Rector, php-cs-fixer) in the core, the API and the storage, PHPStan's result cache of the event storming's analysis, and Vitest's results. Each key starts with a digest of the tool's configuration and the lock files. Each run saves its own cache and restores the latest one of the same configuration.
  - The journeys run in the merge queue, in the job `e2e`, beside the other checks (ADR 0220). It runs `make check-e2e` on a stack started on the runner, from nothing: the stack deployed, its data recreated, then every journey project. A group whose changes need no journey passes the job at once, without a stack. A pull request whose journey fails leaves the queue. The job then keeps Playwright's report (traces, screenshots, the video of each journey that failed) in the artifact `e2e-report`, and the stack's logs (`make logs-save`: its services and its MiniStack's functions) in `e2e-logs`, for 7 days. The journeys are part of neither a pull request's CI nor `make ci`.
    - A developer can still run them in their worktree before the merge, with `make check-e2e`, to catch a broken journey sooner.
    - `make check-e2e` runs on the worktree's running stack, after it gives that stack the branch's functions and the demonstration back. With `FRESH=1`, when no stack is running, or when what defines the stack changed, it starts from nothing: the stack is started again, deployed and its data recreated.
    - Only one checkout on the machine runs the journeys at a time, waiting for a lock. The first failure stops them. Each project's report lands in its own folder: `apps/front/playwright-report/together`, `alone`, `alone-dashboard` (ADR 0117, 0136).
    - `check-e2e` refuses to run in the main checkout, whose data it would recreate. It runs in a worktree and in the CI (`CI` set).
    - Fix a failure and rerun it alone (`FILTER`, `FAILED=1`, `make e2e FAILED=1 E2E_RESULTS=<project> E2E_ARGS=--project=<project>`), never the whole run for it.
  - A pull request also mutates the lines it adds (ADR 0219), in a `mutation <part>` job per part of the code it adds lines to: `core`, `front` (the SPA) and `event-storming` (the event storming's generator). `make changed-checks` names these parts (`mutation-<part>`), from the files the core's Infection and the front's Stryker mutate, their tests and generated files left out. A part the pull request does not touch gets no job. Neither the merge queue nor a push to `dev` or `main` mutates anything.
    - Each job runs `make mutation-<part> BASE=origin/<base>` beside the checks, so it mutates the lines added since the pull request's base, as `make mutation` does locally.
    - Each job publishes the artifact `mutation-<part>`: the tool's JSON report and `summary.md` (`make mutation-artifact`). The summary gives the score, the killed, surviving, not covered, timed out and skipped mutants, and each survivor and each mutant no test covers, by its file, its line and its mutator. The job's summary on GitHub shows the same text.
    - The job fails when the tool cannot run, or when the core skips a mutant (ADR 0196). A score under the threshold does not fail it: the definition of done judges the threshold of 80 % per project ([`tests.md`](tests.md#mutation-testing), ADR 0202).
    - The mutation jobs are not part of the `ci` check that the rulesets require, and `make ci` runs no mutation.
  - `make ci` runs the checks for the changes since `origin/dev`, committed or not (`ALL=1` runs every one). It builds the images, installs the dependencies, checks the contract and writes the walls again when needed (the front's tests read them), then runs the other checks in parallel, each printing its output once it ends. It needs no stack: the API and storage tests run on the checkout's test MiniStack, and the Terraform lint keeps what it downloads in `.cache/`. It stops at the first failure (`FAIL_FAST=1`). When the changes need the journeys, it names `make check-e2e` (`make e2e` on the running stack in the main checkout).
  - Terraform also plans a pull request that touches `apps/*/infra` (`.github/workflows/terraform-plan.yml`, ADR 0060), with one comment per app and instance. Once the pull request is merged into `dev`, Terraform applies it to the `dev` instance (`.github/workflows/terraform-apply-dev.yml`, ADR 0061). Once it is in `main`, Terraform applies it to `prod`, after an approval in the `production` environment (`.github/workflows/terraform-apply-prod.yml`, ADR 0062). Both workflows can be run by hand on their branch (`workflow_dispatch`), and they then apply every app. Run them by hand after the edge changed (ADR 0067), or for a new instance's second apply (ADR 0069).
- A pull request merged into `dev` moves the tickets it refers to (`Refs <backlog>#<n>`) to the QA column of the backlog's project (`.github/workflows/backlog-qa.yml`). The release to `main`, and a pull request closed without merging, leave the board alone. The repository needs the secret `PROJECT_TOKEN` (a fine-grained token with read and write access to the organization's Projects, and read access to the backlog's Issues) and the variables `BACKLOG_OWNER`, `BACKLOG_PROJECT` (its number) and `BACKLOG_REPOSITORY` (`<owner>/<repository>`).
- Commits follow the conventional format (`feat:`, `fix:`, `refactor:`, `chore:`, `docs:`, and `test:` for a red test committed alone before the code that makes it pass). The subject is imperative and 72 characters at most. The body gives the why.
  - The `commit-msg` hook (`.githooks/commit-msg`, installed by `make hooks`) refuses a subject without one of these types followed by `: `, or over 72 characters, and says which rule it breaks. It lets through the subjects git writes itself: a merge, a revert (`Revert "…"`, `Reapply "…"`), and a `fixup!`, `squash!` or `amend!` commit to squash.
  - The CI checks the same rule with the same script (`make/commit-subject.sh`), in the `secrets` check (`make commit-subjects`), on each commit that is in neither `dev` nor `main`: a commit pushed without the hook fails it, named with the rule it breaks. A merge is left out, and a commit still to squash fails (`git rebase --autosquash origin/dev`).
  - No script judges the style of a subject (imperative, plain words): the review does. [`clean-code.md`, section 14](clean-code.md#14-writing-style) sets the writing style of commits, docs and docblocks.
- A branch that takes a decision adds its record (`docs/adr/TEMPLATE.md`) and writes the record's line in the index with `make adr-index` (ADR 0128). `make ci` checks the index against the records' headers. When two branches each add a record, a rebase keeps both lines (`merge=union` in `.gitattributes`), with no conflict to resolve. A pull request that GitHub reports as conflicting on the index alone is rebased locally (`git rebase origin/dev`), and the union merges it.
  - The union judges nothing. A branch that changed its own line after adding it (its title, its status, its renamed file) gets that line back once per commit during the rebase, some of them pointing to a file that no longer exists. So after rebasing a branch that touches the index, and before pushing it, run `make adr-index` to write the index again from the headers, one line per record, and commit the index when it changed (`docs: …`). `make adr-index-check` remains the CI's safety net.
