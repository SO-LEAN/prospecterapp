# The core

What is in force; the reasons are in the records it names (`docs/adr`), read only to know why or before changing it (ADR 0090).

`packages/core` (`prospecter/core`) is the hexagon: the domain (aggregates, value objects, policies, repository interfaces) and the application (use cases by business intent, their ports and services) of the bounded contexts Accounts, PersonalData and Prospecting and their shared kernel, in pure PHP. The bounded contexts and what they publish to each other: `contexts.md`; the language and the rules of each: `docs/domain/`.

## Layout

Grouped by bounded context, then by layer (ADR 0030); `tests/Architecture/BoundedContextsTest` fails when a context uses another one.

The `Domain` of a context is grouped by kind of building block (ADR 0086): `Model/` (aggregates, entities, value objects, enums, the intents among them), `Repository/` (the interfaces of the repositories), `Service/` (the domain services, a rule on a set of aggregates, ADR 0039), `Policy/` (a pure rule without state, `Masking`), `Port/` (what the context asks the others, implemented by an anticorruption layer, ADR 0045), `Event/` and `Exception/`. A folder exists only when it holds something; the shared kernel stays flat, being only model, but for `Event/` and `Exception/`.

- `src/SharedKernel/{Domain,Application}`: what every context shares, kept small: the published identities `AccountId`, `MemberId`, `PersonId` and `OrganizationId`, in `Domain/Event` the bases of every domain event (`DomainEvent`, `OrganizationEvent`, `PersonEvent`, `AccountEvent`), `ReleasesEvents` and `RecordsEvents`, `Email` (in lower case), `PhoneNumber` (E.164, ADR 0072), `ContactDetails`, `LegalIdentity`, `Address` and its `GeoPoint`, `File`, `Slice` (a list newest first and the cursor of what follows, ADR 0049), `SearchKey` and `SearchKeys` (an aggregate is found by the beginning of its name or of its email, without accents, case, spaces nor punctuation, ADR 0071), `Uuid`, the business exceptions in `Domain/Exception` (`BusinessException`, `NotFound`, `BusinessRuleViolation` naming the faulty field, `NotPossibleInItsState`, `NotAllowed`), and in the application `CommandHandler`, `QueryHandler` and the marker `OutputPort` of the output ports of the queries, `EventHandler`, `PublishesEvents`, `RefusalTranslatingHandler`, the port `Events`, `UseCaseRefused` and its `ErrorType`, `FileResponse`, the port `Storage` and `FileStore`, the port `PrivateStorage` (the private files, ADR 0077) and its `Upload`, the port `GeoLocation` and `GeoLocalizer`. Each context keeps its own exceptions in `Domain/Exception` (`UnknownOrganization`...).
- `<Context>/Application/<Intent>/`: one package per use case, CQRS (ADR 0029). A command (`Relocate/Relocate`, readonly data) and its handler (`RelocateHandler`, implements `CommandHandler`, `__invoke(Relocate): void`) change the state and return nothing. A query (`ConsultOrganization/ConsultOrganization`) and its handler (`__invoke(ConsultOrganization, ConsultOrganizationOutput): void`) present a response to the output port its client gives (ADR 0085): each query declares its port beside it (`ConsultOrganizationOutput`, extending the marker `OutputPort`; the ports of the published queries extend nothing, a Contract importing nothing), and the presenter keeping the answer as it is (`KeptOrganization`, `public private(set)`), for the clients that read it rather than show it; only queries give data back. What the intents of a context share stays one level up (`OrganizationSheet`, `FileResponse`); a query reads its read model through a port of `Application/Port` (`OrganizationSheetRetriever`, `FoundOrganizationRetriever`, `ExchangeDetailRetriever`, `TimelineRetriever`, `MyAccountRetriever`, `MemberRetriever`, `PersonCardRetriever`, `ContactPageRetriever`, ADR 0088), doubled in the scenarios by an in-memory retriever reading the `InMemoryDatabase`.

## Rules

- Pure PHP: `composer.json` requires only `php`, `ext-intl` (the normalization of `SearchKey`) and `giggsey/libphonenumber-for-php` (what a phone number is, `PhoneNumber`, ADR 0072), dev tools aside. Never add a framework or infrastructure dependency; the outside is reached through ports (`Port/`, repository interfaces) implemented in `apps/api`.
- Names: the interface says the role, the implementation its technology (`OrganizationRepository`, `DynamoOrganizationRepository`, `InMemoryOrganizationRepository`). No `Impl`, no `Interface` suffix, no CRUD verbs in use cases (`Create`, `Get`, `Update`, `Delete`).
- A command handler is one intent: it loads the aggregate of its intent, calls its intention methods with `by:` the member who acts (the command carries its id as a string; a `MemberId` in Prospecting, the author of what is recorded, the acting member or reader where the rule depends on them: Accounts, PersonalData; `StartProspecting` places and describes the new organization), saves it with `save()`, and returns nothing; a query handler only reads. It changes only the data of its intent, and is reused by another client or a data recovery, never by another use case. No transaction: one aggregate per use case; what other aggregates or contexts must do follows from the events it recorded (ADR 0042).
- Business rules live in the aggregates: named constructors (`Organization::prospectedBy`, `Account::open`, `Member::register`), intention methods (`relocateTo`, `removeLogo`), no setters; an invariant is checked before the change. Aggregates reference each other by identity, never by object.
- The client gives the identity of what it creates (a UUID v7 string in the command) and the moment of every command (`executedAt`); the intention methods take it (`at:`) and the aggregates keep `createdAt` and `modifiedAt` (ADR 0036). A rule on a set of aggregates, out of reach of one of them, is a domain service of the hexagon (ADR 0039): `EmailUniqueness` keeps an email unique among the persons of an account for a purpose (PersonalData), among the organizations of an account (Prospecting); it asks the repository (`isEmailUsed()`), and the handler calls it before `save()`. Repositories and doubles answer questions, they never decide.
- The domain never crosses the application (ADR 0035): requests are flat data (strings, numbers, `\DateTimeImmutable`, `\SplFileInfo`), responses the same plus data structures of the application, built by named constructors (`FileResponse::orNone()`), intentions by name; `tests/Architecture/ApplicationBoundaryTest` fails otherwise. A handler builds the value objects and implements `CommandHandler`, `QueryHandler` or `EventHandler`, without error handling: clients call it through the decorator `RefusalTranslatingHandler`, which translates a `BusinessException` into `UseCaseRefused::because()` (type, message of the domain, field, the domain exception as previous); infrastructure exceptions go through. Exceptions get named constructors (`UnknownOrganization::identifiedBy()`, `BusinessRuleViolation::because()`). A refusal worth its own words has its own class, extending its kind (`InvalidPhoneNumber`, `NoLogoToRemove`), with what it is about in its context: its class names it to the clients, which word it (ADR 0073); a new one gets its French words in `refusals` of `apps/front/src/shared/i18n/fr.ts` (`RefusalsAreWordedTest` of the API). Value objects are `final readonly`. Aggregates hold their value objects as they are (`private ?Address $address`): the domain knows nothing of persistence, the API mapping adapts to it (ADR 0028, 0048). An aggregate has no getter for the reading (ADR 0088): its repository and the retrievers read its state by reflection (`Hydrator` in the API, `StateOf` in the tests, `AggregateStateIsReadByItsRepository` telling PHPStan); it exposes its identity, what its repository and the domain services ask, and the questions of its rules. A new property of an aggregate or of a value object requires a change of its document in the API (`apps/api/src/<Context>/Persistence/*Document.php`, ADR 0048). A class of a domain is `final`, unless the domain extends it (`tests/Architecture/DomainClassesAreFinalTest`). A list is sliced, never counted: the repositories, or the retrievers of read models (ADR 0088: `FoundOrganizationRetriever`, a port of `Application/Port`, reading the table of the aggregate without restoring it), answer a slice after a cursor, and search by the `searchKeys()` of the aggregate.
- Authentication, roles and the access to a resource are not the business of the core in Prospecting (ADR 0081): the API checks with its voters that the organization or the exchange belongs to the account of the member, and the right to manage personal data an intention needs; a request carries the id of the member who acts, the author of what is recorded, so that a use case also runs without a signed-in member. What a member reads still depends on them (`Prospectors`: the text flagged, the attachments hidden). PersonalData decides what its reader sees and may do, and checks that a person belongs to their account (`Readers`); Accounts that an account is managed by its members.
- An aggregate offers its possible intents (an organization by the policy `OrganizationPossibilities`, given the facts of its state, which the retrievers of its sheet ask too, ADR 0088; an exchange by `ExchangePossibilities`, its retriever also asking `ExchangeConformity` and `ExchangeReading` what its reader reads; an account by `AccountPossibilities`, given whether the member belongs to it, and the right to read the personal data by `PersonalDataRight`, asked by `Member::readsPersonalData()` and by the retrievers of Accounts; a person by `PersonPossibilities` given their reader, read in clear or masked as `PersonReading` says), which the API turns into links (ADR 0027; in Prospecting, those its voters grant too, ADR 0081); every intention method starts with the same check (`ensurePossible`) and throws `NotPossibleInItsState` for what is not offered. A new intention gets a case in the intent enum, a check, and a line in `OrganizationIntentsTest`, `ExchangeTest`, `AccountIntentsTest` or `PersonIntentsTest`.
- Domain events (ADR 0042, 0043): every intention method records one event in the past tense (`recordThat(new Relocated(...))`), with identities only, never personal data; an aggregate `implements ReleasesEvents` and `use RecordsEvents`. Its events live in `<Context>/Domain/Event`, and never leave the context. The handler `use PublishesEvents` and calls `publishWhatHappenedTo($aggregate)` after saving it: the events go on the port `Events`, delivered synchronously, within the use case. A new intention gets its event, and its intents test checks it is recorded. What another context must know is an integration event (ADR 0046): plain data in `<Context>/Contract/Event` (`ContactCollected`, `ContactForgotten` of PersonalData, `ContactsLeftWithoutOrganization` of Prospecting), built from the domain event and published by a handler of the emitting context (`PublishContactCollectedHandler`). The other context reacts with an `EventHandler` (`__invoke(TheIntegrationEvent)`), translating it into its words, as the member who did the gesture, through the intention methods: no rights bypassed. Only integration events cross contexts (`tests/Architecture/BoundedContextsTest`). A Contract (`<Context>/Contract/{Service,Event}`, ADR 0047) is plain data and the interfaces of its services (ADR 0089), importing nothing (`tests/Architecture/ContractTest`): what a context promises the others, the contract package of the context deployed apart. A contact is never alone: it is collected for at least one organization, and a contact no organization names any more is erased.
- Services (`FileStore`, `GeoLocalizer`, `EmailUniqueness`, `OrphanContacts`, `ContactOrganizations`, `AttachedFiles`) and the decorator `RefusalTranslatingHandler` are real classes of the hexagon, never doubled. They are injected into the handlers, never built by them (ADR 0044): a constructor builds nothing, a service is built by the client (the container of the API, `tests/Acceptance/Application` in the scenarios); `make lint` fails otherwise (`packages/phpstan-rules/DependenciesAreInjectedRule`).
- The API sends commands on a synchronous Symfony Messenger bus (every `CommandHandler` is registered on it through `RefusalTranslatingHandler`) and receives the query handlers already wrapped in the same decorator, by the name of their intent (`RefusalTranslatingHandler $consultOrganization`), and gives each call its output port (`($this->consultOrganization)(new ConsultOrganization($id), $presenter)`); it builds commands with named arguments: renaming a property breaks it (PHPStan and the API tests catch it), so change the core and the API in the same commit.
- The core knows no bus: `tests/Acceptance/Application` sends a command to its handler (found by the type of `__invoke()`, as Messenger does), through `RefusalTranslatingHandler` like the API, and is the only place that knows how a handler is called.
- Clean code (`docs/architecture/clean-code.md`): names instead of explanatory comments, docblocks only for generics and array shapes.
