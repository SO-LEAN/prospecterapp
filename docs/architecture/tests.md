# Testing the core

This document states the rules in force. The decision records (`docs/adr`) explain why: read them only for that, or before changing a rule (ADR 0090).

The tests run in two loops, as in *Growing Object-Oriented Software*:

- **Acceptance (outer loop)**: a Gherkin scenario, in French, states a business rule at the hexagon's entrance. It is written first and stays red until the rule works. It knows requests, responses and the state of the outside world. It never knows how a use case does its job, so refactoring does not touch it. Access to a Prospecting resource is not a core rule: the resource is unknown to another account, and refused without the right to manage personal data. The API's voters check this access, and the API tests prove it (ADR 0081).
- **Unit (inner loop)**: PHPUnit covers what a scenario cannot reach or would express clumsily: pure logic rich in edge cases. `tests/Domain` holds the tests of `Email` and the identities, and the intent tests of `Organization`, `Account` and `Person`. An intent test checks that every intention is refused exactly when the aggregate does not offer it, that is, when its API link is missing. `tests/Application` tests how refusals are translated. `tests/Architecture` tests the boundaries. A unit test checks a behaviour, never a structure (no getter or setter tests).

## Nothing inside the hexagon is doubled

Aggregates, value objects, handlers, services and decorators are the real classes. The services are `FileStore`, `GeoLocalizer`, `EmailUniqueness`, `ReferenceUniqueness` (PersonalData's and Prospecting's), `SiretUniqueness`, `WebsiteUniqueness`, `DuplicateSuspicion` (PersonalData's and Prospecting's), `OrphanContacts` and `ContactOrganizations`. `Application` builds them once and injects them into the handlers (ADR 0044). The decorators are `RefusalTranslating…Handler` and `Transactional…Handler`. Only the ports, the interfaces to the outside, get test implementations. These live in `tests/Double`. They are working implementations, not mocks; the tests use no mocking library.

## Layout

```
features/*.feature              the business rules, French Gherkin (# language: fr)
tests/Acceptance/Application    the hexagon wired to the doubles; the only place that calls a handler
tests/Acceptance/Context/       step definitions (ScenarioContext shares the state, SharesTheScenario gathers it)
tests/Acceptance/Vocabulary     the tables' French labels, and how they read entities and value objects
tests/Acceptance/Expect         assertions (PHPUnit's need its runner to describe a failure)
tests/Double/                   the ports' test implementations; StateOf, the private state of an aggregate, each property
                                read as the type expected of it (State)
tests/Support/                  PHPUnit: the helpers of the tests (State)
tests/Domain/                   PHPUnit: value objects rich in edge cases, intents refused exactly when not offered
tests/Application/              PHPUnit: the handlers' decorators: translating the domain's refusals (UseCaseRefused,
                                RefusalTranslating…Handler), and the unit of work they begin and commit (Transactional…Handler)
tests/Architecture/             PHPUnit: no bounded context uses another one except through its Contract (the
                                contexts are the folders of src), a domain uses neither its application nor its
                                Contract, src imports only PHP and the permitted vendors, a Contract imports nothing, no domain class in a request or a response, every handler is a
                                CommandHandler, a QueryHandler or an EventHandler, every event handler is subscribed in the scenarios,
                                only a publication of facts subscribes to a parent event (ParentEventsFeedOnlyFactsTest),
                                the shared kernel holds no identity but AccountId and MemberId (SharedIdentitiesTest),
                                no class of the shared kernel serves a single context (SharedKernelServesSeveralContextsTest)
tests/Mutation/                 each feature's scenarios as a PHPUnit test, for mutation testing only
```

The scenarios do not know the API's command bus. `Application::dispatch()` sends a command to its handler. A query is called directly, and the core's presenter keeps its answer (`KeptOrganization`, ADR 0085). Each goes through the decorators of its kind, as in the API. A command runs in its unit of work, then each of its reactions runs in its own (`SynchronousEvents::deliverAfter()`). A scenario reads the response that the `Application` method returns.

Every core event handler, including the translators publishing the integration events (ADR 0046), reacts in the scenarios as it does in the API (`Application::translators()` and `reactions()`). `tests/Architecture/EventHandlersSubscribedTest` fails when one is missing. A scenario checks a gesture's side effects in the other contexts, never the events themselves. There are two exceptions: a rule about their delivery, and a published event that is part of a context's contract (Prospecting's and PersonalData's facts, `publier-les-faits-de-prospecting.feature`, `publier-les-faits-de-personaldata.feature`). Such a scenario checks how many are published (`SynchronousEvents::published()`), or a reaction delivered again (`Application::publishAgain()`, `arreter-de-prospecter.feature`). A scenario may add a reaction of its own after them (`Application::alsoReactWith()`). In `une-commande-ecrit-tout-ou-rien.feature`, `FailingReaction` writes before it throws, and its event ends up among the failures. The intent tests check that an accepted intention records its event.

The services the contexts publish (ADR 0045, 0089, `Contract/Service`) are called through `Application::consultMembers()`, `whichAreContacts()`, `whichAreProspected()`, `listOrganizationFacts()`, `listExchangeFacts()`, `listContactFacts()`, `listAccounts()`, `whichHaveAConnectedCalendar()` and `presentMembers()`, as the anticorruption layers call them, in `features/langage-publie.feature`. `Application` plays the client. It provides the identities of what is created (`newIdentity()`, time-ordered UUIDs from `TimeOrderedUuids`) and the commands' moment (`now()`, set by `nous sommes le "2026-10-20 14:00"`). A refusal is the last call's `UseCaseRefused` (`refusal()`).

## Adding or changing a rule

1. Write the scenario in the intent's feature (one feature per use case, named after it in French: `demenager.feature` for `Relocate`), with the words already in use (`Vocabulary` lists the table labels). Run `make test-core`. It must fail, for the expected reason.
2. When a step is missing, Behat prints a snippet. Add it to the domain's context (`OrganizationContext`, `AccountContext`, `PersonalDataContext`), or to `ScenarioContext` for shared steps. Steps arrange data through the aggregates and repositories (and save what they change), act through `Application`, and assert on responses or on the stored state.
3. A new port gets a working double in `tests/Double` that behaves like its real adapter.
4. Make it pass in `src`, then refactor with the scenarios green.
5. Run `make test-core && make lint`, then `make test` (the API uses the core).

Check that a scenario really protects its rule: break the rule in `src`, see the scenario fail, then restore it. `make mutation` does this for every line the branch adds ([below](#mutation-testing)).

## API tests

- `tests/Api` holds functional tests built on `Base/ApiTestCase`. Its `login()` really signs a member in on MiniStack's `prospecter-test` user pool (`AccessTokenTest`, `SignInTest`). The tables with the `prospecter-test` prefix and the user pool are recreated once per test process, with the demonstration's data and members. Each test then gets them back as they were, whatever ran before it (ADR 0180). `Base/DataOfTheDemonstration` rewrites the items a test changed or removed, deletes those it added and restores the accounts' secrets. `Base/MembersOfTheDemonstration` deletes the users and pool clients a test added, and restores each demonstration member's login email and password. All of this runs on the test MiniStack (`ministack-test`), never on the stack's MiniStack. There is one per checkout, with no port, state or Lambdas, and `make test-api` starts it (ADR 0109). The tests run in four processes with ParaTest (`TEST_PROCESSES=`), each on its own tables and user pool (`TEST_TOKEN` in `.env.test`: `prospecter-test1`…). The host is `api.test.prospecter.io`. The variables are in `.env.test`.
- `tests/Shared/Messaging/EventCodecTest` checks that every core event class is listed and survives a JSON round trip, under its context's source. `SynchronousDeliveryTest` checks three rules. An event published by a reaction inherits its cause one level deeper. One command's events share its correlation. Two reactions answering each other stop beyond `EventLoop::MAX_EVENT_DEPTH`. `tests/Architecture/ReactionsAreSubscribedTest` checks that every core event handler is a translator or a subscription in `config/subscriptions.json`. That file names only known reactions and events. A domain event is subscribed to in its own context only. For the MCP server (ADR 0163), `tests/Architecture/EveryEndpointHasItsToolTest` fails and names each member endpoint without its tool (except those in its `NEVER` and `TO_COVER` lists), each reading tool without `readOnlyHint`, and each route it names that no longer exists. `tests/Api/ReadingToolsApiTest` asserts that each tool returns what its endpoint returns, the resource or its problem, to a prospector, an assistant, an administrator, a member who is not a prospector, and a member of another account (`ApiTestCase::aMemberOfAnotherAccount()`).
- `tests/Shared/DynamoUnitOfWorkTest` tests the unit of work on MiniStack's tables: levels; one write per item; two additions to an item summed; a put replacing another while keeping its condition on the item as stored; the ceiling of 100; the refusal carried by a write; what a read sees before the commit; the lock on the revision of an item read, cancelled once the item is changed or created meanwhile, by key or among others, a delete too, none outside a unit, read again by the next unit. The repository tests for organizations, persons and exchanges check that a save or a removal is cancelled over a change another request made meanwhile (`ApiTestCase::asAnotherRequest()`, the table with a unit of its own, ADR 0181). In `tests/Api/ConcurrentWritesApiTest`, another request attaches a contact to an organization just before a command writes it (`Tests\App\Double\OrganizationChangedMeanwhile`). A collected or attached contact is replayed: both contacts are named, and both are erased with the organization. A change is refused (409 `changedMeanwhile`). An addition still cancelled after three replays is refused. A file attached to an exchange that was corrected meanwhile is refused (`Tests\App\Double\ExchangeChangedMeanwhile`). With the `sync` delivery, a collected contact is attached within its command and replayed. With `outbox`, the worker applies the reaction attaching it again (ADR 0104). In `tests/Api/AllOrNothingApiTest`, with the `sync` delivery, a reaction that refuses or fails leaves the tables as they were (`Tests\App\Double\FailingReaction`, a test subscription the test arms, the client not rebooted). An email another request took meanwhile (`Tests\App\Double\EmailTakenMeanwhile`) is refused at commit and translated like any refusal.
- The outbox (ADR 0098): `tests/Shared/CommitOutboxTest` (one item at the outermost commit; a commit publishing in two contexts refused; none without an event; a discarded unit throws its events away; none for a unit refused at commit after its events were delivered; the item ceiling). `tests/Api/CommitOutboxApiTest` (a command with `INTEGRATION_EVENTS_DELIVERY=outbox`, set by `Base/DeliversThroughTheOutbox`, which rebuilds the kernel's services for a console command: one item with its domain and integration events, expiring a week later). `tests/SignIn/{OpenAccountCommandTest,RegisterMemberCommandTest}` (a console gesture commits in Accounts alone, ADR 0100). `tests/Shared/TablesTest` (the tables' stream and TTL). It keeps each `PutEvents` and fails entries when asked. `OutboxRelayTest` (ten entries per put and under 256 KB, a partial failure failing the batch) and `RepublishOutboxCommandTest` use it.
- The worker (ADR 0101, 0102, 0104): `tests/Shared/Messaging/IntegrationEventConsumerTest` gives `IntegrationEventConsumer` invocations shaped like the input transformer's, internal and between contexts, with the `outbox` delivery. It checks that what a reaction publishes goes one level deeper into its outbox; that an event delivered twice is applied once; that the inbox is in the table of the subscription's context; that two subscriptions to one event do not replay each other; that a refusal, an event too deep, an unknown subscription or an unreadable event goes into the failures without a retry; that a refusal is logged with its `eventId`, its correlation, its `reason` and its `field` (`Tests\App\Double\InMemoryLogger`); and that a thrown failure writes nothing, not even the inbox. `tests/Shared/Messaging/QueuedIntegrationEventConsumerTest` tests the local stack's worker (ADR 0131): an invocation taken from its queue as the rule sends it, one given directly, a failure thrown before its third receive and kept as `RetriesExhausted` at that receive, a refusal kept once. `tests/Shared/RedriveIntegrationFailuresCommandTest` tests the redrive. SQS and Lambda are `Tests\App\Double\InMemorySqs` and `InMemoryLambda`, the SDK clients' handlers in the tests. The bus rules, Lambda's retries and its destination are tested on an AWS instance, since MiniStack does not run them from a rule. A conflict is applied again three times at most, then thrown. A subscription naming a handler per event gives each event its own. An event it does not listen to is refused.
- `tests/<Context>` tests the adapters on their real table or service:
  - `DynamoPersonRepositoryTest`: the reservation refuses an email taken meanwhile.
  - `DynamoOrganizationFactsRetrieverTest`, `DynamoExchangeFactsRetrieverTest`, `DynamoContactFactsRetrieverTest`: each save's revision, the facts as the unit of work is about to write them, absent once removed, none for a member's profile, an account's facts by slice.
  - `DynamoAccountListRetrieverTest`: the accounts by slice, the keys rewritten.
  - `DynamoCalendarRetrieverTest`: a period's exchanges whatever their status, moved, removed, the links rewritten.
  - `DynamoToDoCalendarTest`: a period's to-dos by their due date on their reader's days, revised, erased, the links rewritten.
  - `OrganizationSearchTest`: found by the beginning of the name or the email, the keys rewritten.
  - `DynamoCampaignRepositoryTest`: a campaign restored as saved, a frozen one with its recipients in order, its sheet, an account's campaigns newest first, those keeping a contact, a removed one or another account's one unknown.
  - `GeoplateformeGeoLocationTest` and `SignIn/RsaPublicKeyTest`.

  `tests/Architecture` tests the boundaries (contexts, domain behind the application, one table per context) and the shape of the controllers (`ControllersExtendNothingTest`). `BoundedContextsTest` reads the contexts from the core's folders. A context folder uses another context only through its Contract, except where it composes one on purpose (`Connectors` composes Prospecting). Every other folder of `src` is named in the test with its reason, so a new folder fails until it is placed. `tests/Local` tests what only the local stack has (the profiler, its CORS). A test that fails because of a MiniStack limit is skipped with its reason. A dev instance on AWS is the safety net.
- `tests/Reporting` (ADR 0104): `DynamoFactRepositoryTest` (an older revision ignored; a terminal fact wins and is forgotten 15 days later; two simultaneous recordings for one account both count; a fact changed meanwhile cancels the recording written from what was read; an exchange moved to another month; several facts in one unit). `RebuildFiguresCommandTest` (the demonstration's figures counted again, the former version removed, nothing written except Reporting's table, the number of accounts counted reported, two, then none without failing). `FiguresFollowTheGesturesTest` (the figures follow the API's gestures, with the `sync` delivery).
- `tests/Consistency` (ADR 0105): `CheckConsistencyCommandTest` runs `app:consistency:check` on the demonstration, its figures counted again. First nothing is reported. Then each discrepancy is written by hand in the tables: a figure, a month's exchanges, no active version, a contact attached to no organization, a forgotten contact still attached, a member without a profile, an account without a member, an exchange of an organization no longer prospected, an account without its account-list key, an exchange without the key listing it in its account, an upcoming exchange of a member connected to Google not synced in their calendar, a contact to attach past their erasure day (a contact to attach waiting with no meeting), the tags of an organization no longer prospected or of a forgotten contact, a frozen campaign still keeping a forgotten contact. Or a message is put in the worker's or the relay's failures (`InMemorySqs` counts the waiting messages). Each is reported with its account and its correction. `--account` limits the check to one account. The check leaves the tables unchanged.
- Unit tests extend PHPUnit's `TestCase` and use hand-written doubles (`tests/Double`), no mocking library.
- PHPUnit 13: attributes only (`#[DataProvider]`, `#[Group]`), static data providers, abstract base classes named `*TestCase`.

`tests/StorageTest` tests the storage as the API and the browsers use it. ## No service outside the stack

No test depends on a service outside the local stack. The test doubles it, so that a red test always means a defect in Prospecter, never a third party's failure (ADR 0092). The API tests give the geocoder an address with no host (`APP_GEOCODER_URL` in `.env.test`, `GeoplateformeGeoLocationTest` on a `MockHttpClient`). The double `tests/Double/OutsideServices` (`framework.http_client.mock_response_factory`) answers every request leaving the API. It answers empty unless a test makes the geocoder place an address (`DashboardApiTest`) or the company directory list companies (`EstablishmentsApiTest`). The directory's answer is kept for the test's first request only, since the kernel resets the double when it boots again. After that request, the directory fails. `RechercheEntreprisesDirectoryTest` runs on a `MockHttpClient`, never through an alias of a framework service. EventBridge is its in-memory double (`InMemoryEventBridge`). Google is the double behind it (`Tests\App\Double\GoogleDouble`). It is kept between the requests of a client that does not reboot. Its calendars keep the pushed events (`PushToGoogleApiTest`). Its Gmail keeps the watched topics and the stops, the messages a test makes it receive, its history, its profile and each message (`GmailNotificationsApiTest`: a notified e-mail imported as an exchange). Its keys are those a test draws and publishes, and they sign a Gmail notification's token (`GmailNotificationsApiTest`, ADR 0154). `GoogleProviderAccessTest` and `GoogleCalendarTest` run on a `MockHttpClient`. An account loses its Google client when its administrator removes it (`ConnectorsApiTest`, ADR 0125). SSM is the test MiniStack's (`DynamoProviderClientRepositoryTest`). It refuses the operations a test names, as a role without the permissions would (`RefusingSsm`, an SDK client middleware). In `GoogleClientApiTest`, a gesture whose secret SSM refuses is a 503 `secretsUnavailable` and keeps the former client). The main journey uses nginx's Google double (`local-stack.md`).

## No test reads the real clock

A test passes the same today, tomorrow and in a year: what it tests gets a fixed moment, never the moment it runs at (ADR 0150).

- **The core**: the scenarios run on `Application`'s moment (`FIRST_DAY`, moved by `il est …`). `TimeOrderedUuids` counts identities from a fixed millisecond. A unit test names its moment (`private const string AT`).
- **The API**: the controllers read the `when@test` `clock`, a `MockClock` at `2026-10-15 09:00:00 UTC` (`theClockShows()` moves it). A test building an aggregate or an event uses that moment (`ApiTestCase::THE_MOMENT_OF_THE_TESTS`). It uses a constant of its own only for a different moment. What the tables forget (the outbox, the inbox, the terminal facts, the authorizations) is counted from `app.commit_clock`, a `MockClock` at `2100-01-01`. This moment is long after any run, since MiniStack forgets on the real clock. One read of the real clock remains: the clock checking the tokens MiniStack's Cognito issues on it (`HandlePlannedExchangeApiTest`).
- **The front**: `src/test/setup.ts` sets the date of every Vitest test to `THE_MOMENT_OF_THE_TESTS` (`src/test/the-moment-of-the-tests.ts`), a Wednesday morning, with real timers. A test moves it with `vi.setSystemTime`, fakes its timers with `vi.useFakeTimers` (from the set date), and reads it with `theMomentOfTheTest()`. A pure function is given its moment.
- **The journeys** read the real clock only to name what they create (`e2e/unique.ts`, the named exception). Run names stay readable and in run order, and the moment decides nothing. Their deadline is measured with `performance.now()`.
- **The rules**: `make lint` refuses a test that reads the real clock. PHPStan checks the core, the API and the storage (`packages/phpstan-rules/TestsReadNoRealClockRule`: `new DateTimeImmutable()` without a moment or with one relative to now, `time()`, `microtime()`, `date()` without a timestamp, `NativeClock`, `MockClock` without a moment, `Clock::get()`). Biome checks the front's tests and journeys (`lint/real-clock.grit`: `Date.now()`, `new Date()`). An exception is named where it is made: `@phpstan-ignore prospecter.realClock (<why>)`, `// biome-ignore lint/plugin: <why>`. A `packages/phpstan-rules` rule is tested in the core's PHPUnit (`tests/PHPStan`, a `RuleTestCase`), on fixtures outside every analysed path (`packages/phpstan-rules/fixtures`, whose `tests/` folder stands for a test).
- **A year later**: `make test CLOCK_SHIFT=+365d` runs the core, the storage and the front on a system clock moved by `libfaketime` (built in `docker/php`, installed in `docker/node`). Their monotonic clock stays untouched. The API stays on the real clock, since its tests sign in on MiniStack's Cognito.

## The journeys

- **What a journey is for** (ADR 0122): a journey covers only what no other test covers end to end. A journey stays when what it checks crosses one of these parts: the sign-in on Cognito, the API in its Lambda, a messaging reaction (outbox, relay, worker), a storage file, a map rendered by MapLibre, or what only a real browser computes (styles, layout, phone gestures). These journeys are the main journey, the console gestures, the dashboard figures, stopping prospecting an organization with many exchanges, a file attached to an exchange, the maps, the sign-in screen, and the shell and its cursors. A screen (what it shows, a form, a list, the links it offers) is tested in Vitest. The test renders a component with Testing Library, or the SPA on its routes (`src/test/render-the-spa.tsx`) when a check crosses the router or the layout. The API is doubled through `fetch`. An API rule (an access, a refusal, a reaction delivered at once) is an API test. A pull request removing a journey names the test that takes over each of its checks. The base set does not grow again. A new journey is accepted only when it crosses one of these parts. A new check of a part that a journey already crosses extends that journey instead of adding one.
- `make e2e` runs Playwright on the checkout's running stack (`apps/front/e2e`; a worktree runs its own, ADR 0116). In a worktree, `make check-e2e` runs them once the development is done. It runs them on the stack as it runs, or from nothing with `FRESH=1` or when no stack runs. From nothing, the stack is first restarted and deployed, and its data recreated. Only one checkout at a time on the machine runs them, `make e2e` included: each one waits for a lock in the shared git directory. The journeys are prepared once for both projects. The first failure stops them, and the journeys running alone do not run when one running together failed. Neither the CI nor `make ci` runs them (ADR 0121). `FAILED=1` reruns those that failed last, and `E2E_RESULTS` names the project.
  - The journeys first run together (ADR 0117: two at a time, `E2E_WORKERS`). After them, two projects run one after the other, each alone (ADR 0136). First comes the `alone` project: the main journey, which signs its member out everywhere. Then comes the `alone-dashboard` project: the dashboard. It reads a figure counted from nothing only once the journeys running together are done. It reads it in the account the console opened for the run, which no other journey changes (ADR 0122). A journey reading what the others change in the account also runs after them. `check-e2e` runs `--project=alone --no-deps`, then `--project=alone-dashboard --no-deps`, each in its own results folder (`E2E_RESULTS`).
  - Stopping prospecting an organization with many exchanges is the longest journey running together, and it starts first. It is in the `together-longest` project, listed before `together` (Playwright runs a phase's projects in configuration order; `check-e2e` runs `--project='together*'`).
  - Meanwhile `check-e2e` counts the figures while the others run (`make db FIGURES=later`). The API calls nginx's geocoder double (`http://nginx:8081/search`, `docker/nginx/conf.d/geocoder-double.conf`). The double places a known place (Strasbourg) at a fixed position in its municipality, and places no other address, as the IGN service answers. A double that does not answer stops the journeys before they start. Afterwards, whatever the result, and with `make start`, the API calls the IGN again.
  - Before the journeys, `make e2e` doubles the geocoder. This recycles the API's containers and restarts as many as the journeys use at once. Meanwhile it warms the relay and the worker (eight worker containers, since a gesture has several reactions, its facts among them). Then it opens an account and registers a member through the console (`E2E_RUN`). It retries the registration until the worker has written the founder. `console-gestures.spec.ts` signs the member in, and `dashboard-figures.spec.ts` signs the founder in. The reactions write their member and profile. Without `E2E_RUN`, both are skipped.
  - It warms as many API functions as the journeys call at once (`wait-for-the-stack.ts`). That is ten per page, per worker: an organization's card and what the shell reads on every page, its banner's connections and my booking page, my reminders, the count of my exchanges to process and my day. One more function would start its container during a journey, which takes about ten seconds.
  - It then waits for the sign-in screen rendered in Chromium, while the dev server transforms the SPA's modules as it starts (`server.warmup` in `vite.config.ts`). The first journey after a deployment used to meet a SPA not yet rendered.
- A journey takes its `test` from `e2e/fixtures.ts` (Biome refuses it from `@playwright/test`). With it, the maps get their style from a double, without tiles, credited as the real one. A journey whose pages call a host outside the stack, over HTTP or WebSocket, fails and names that host (`outside-the-stack.spec.ts`). A service a journey needs is doubled by its own route (`page.route`, `context.route`), and that route wins. Such a route can serve an API resource changed to suit the journey (the organizations given every contact line in `map-popup.spec.ts`, a name too long for a phone in `mobile-zoom.spec.ts`).
- Some journeys check what a screen shows when signed in (the maps, their popups, the phone). The journeys of such a file sign in once per file (`signInOncePerFile` in `e2e/sign-in.ts`, ADR 0122). The session that the SPA keeps in its tab's storage is given to each journey's page before the page loads. The sign-in itself belongs to the main journey and to the sign-in screen's journey.
- A journey needing a new place adds it to the double's map.
- A journey passes whatever the database holds. It passes right after `make install` (the demonstration data only) as well as after other journeys ran. A journey comparing screenshots acts where its gesture changes the picture whatever the data. A single organization's map is centred on its marker over the double's plain background, so `mobile-zoom.spec.ts` pinches it away from its centre.

## Mutation testing

Mutation testing shows what a branch's tests protect (ADR 0091, 0202). A tool changes a line the branch adds (a mutant: a condition inverted, a call removed, a value changed) and runs the tests covering it. A mutant they let pass **survives**: the tests do not see that change.

- `make mutation` runs the core, then the front, on the lines added since `origin/dev`, committed or not (`BASE=` for another reference). A new file counts once it is added to git. A project where the branch adds no line in `src` runs nothing. `make mutation-api` runs the API, on demand (on MiniStack), and takes minutes per mutant.
- **The core**: Infection on PHPUnit (`infection.json5`, `tests/Mutation/phpunit.xml.dist`), the unit tests and the scenarios together. Infection does not know Behat. It mutates nothing that a PHPUnit test does not cover, use cases included. So `tests/Mutation/ScenariosTest` runs each feature's scenarios in its process, and PHPUnit records the test's coverage. Behat runs there with `--xdebug` (without it, Behat restarts PHP without Xdebug and the coverage is lost), and its error handlers are removed afterwards. There is one test per feature: booting Behat for each scenario would take too long. `make test-core` does not run the scenarios twice (`phpunit.xml.dist` leaves `tests/Mutation` out).
- **A busy aggregate** (`Exchange`, whose lines many features cross): Infection skips a mutant (S) when its covering tests took longer than `timeout` in the first run, which runs under Xdebug. The mutant's own run does not count: it runs without Xdebug, the fastest tests first, and stops at the first failing one (ADR 0196). The core's `timeout` (600 s) is above that whole first run, so no mutant is skipped. A unit test kills a mutant in milliseconds, and a scenario in seconds. A survivor costs at most the whole suite without Xdebug, some 30 s. `make mutation` prints the number of skipped mutants and fails when there is one, before the front runs, since no test judges a skipped mutant's lines. Then either raise the `timeout` of `infection.json5` above the first run (its time is printed at the end), or, when that is not possible, list the skipped mutants in the pull request and apply them by hand.
- **The API**: Infection on PHPUnit, 4 processes, each with its own tables and user pool on the test MiniStack (`TEST_TOKEN` in `.env.test`: `prospecter-test1`…, left in place). A line most tests cross is skipped (S) once past the timeout.
- **The front**: Stryker with Vitest (`stryker.config.json`), with per-test coverage, on the ranges of the added lines (Stryker reads no git diff). It skips the tests, the generated files and the shadcn components (`src/shared/ui`: class names no test reads). Stryker allows its first run of every test 15 minutes (`dryRunTimeoutMinutes`): in a worktree that run nears 5 minutes, Stryker's default limit.
- **The definition of done** (ADR 0202): the prospecter plugin's `/prospecter:dod` runs `make mutation` on its first pass, in the background, while its reviewer reads the branch. It runs under the journeys' lock, shared by every checkout on the machine: never alongside the journeys or another mutation run. The definition of done runs `make ci` only after it. A later pass and a rebase run no mutation, and `make mutation-api` is never part of it. When Stryker's first run fails on a test the branch wrote, that test is fixed. When the run times out, the definition of done runs the mutation once more. A project still without a score is `not measured` in the pull request, with the reason.
- **The threshold is 80 % per project**, on the added lines. The core's score is Infection's exact `msi` (`var/mutation-summary.json`), the mutants no test covers counted in. The front's score is the `total` of Stryker's `All files` line. The pull request's `## Mutation` section gives each project's score, as measured before the kills, or `not measured` and why. Under the threshold, each survivor (its path and line, its mutator) comes with its test or its justification. At or over it, the survivors are only listed.
- **Reading a survivor**: a project at or over the threshold lists its survivors in the pull request, and nothing more. Under the threshold, each survivor is killed or justified. Killed: a test committed alone (`test: …`), green first, then red against the mutant applied by hand, then green once the file is restored. The TDD log shows these three runs. Justified: an equivalent mutant, with no effect a member or a caller can observe (a cast with no effect, the same result another way), in one line of the pull request. The reviewer reads the log itself and judges each justification. A mutant that changes something observable (a value returned or shown, a refusal, a boundary, an event recorded) is no equivalent, and needs a test. Equivalent mutants do not make the threshold arbitrary: it only triggers that review, and each one is accepted on its own justification.
- Mutation testing is part of neither `make ci` nor the CI: the first run of every test, with its coverage, takes minutes. Reports: `var/mutation.log` (core, API), `reports/mutation.json` (front).
