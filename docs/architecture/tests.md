# Testing the core

Two loops, as in *Growing Object-Oriented Software*:

- **Acceptance (outer loop)**: a Gherkin scenario, in French, states a business rule at the entrance of the hexagon. It is written first and stays red until the rule works. It knows requests, responses and the state of the outside world, never how a use case does its job, so refactoring does not touch it. The access to a resource of Prospecting (unknown for another account, refused without the right to manage personal data) is no rule of the core: the voters of the API check it, and its tests prove it (ADR 0081).
- **Unit (inner loop)**: PHPUnit for what a scenario cannot reach or would express clumsily for pure logic rich in edge cases (`tests/Domain`: `Email`, identities, and the intents tests of `Organization`, `Account` and `Person`: every intention is refused exactly when the aggregate does not offer it, i.e. when its API link is missing; `tests/Application`: the translation of the refusals; `tests/Architecture`: the boundaries). A unit test checks a behaviour, never a structure (no getter and setter tests).

## Nothing inside the hexagon is doubled

Aggregates, value objects, handlers, services (`FileStore`, `GeoLocalizer`, `EmailUniqueness`, `OrphanContacts`, `ContactOrganizations`, built once by `Application` and injected into the handlers, ADR 0044) and the decorators (`RefusalTranslating…Handler`, `Transactional…Handler`) are the real classes. Only the ports, the interfaces towards the outside, get test implementations, in `tests/Double`. They are working implementations, not mocks; no mocking library is used.

## Layout

```
features/*.feature              the business rules, French Gherkin (# language: fr)
tests/Acceptance/Application    the hexagon wired to the doubles; the only place that calls a handler
tests/Acceptance/Context/       step definitions (ScenarioContext shares the state, SharesTheScenario gathers it)
tests/Acceptance/Vocabulary     French labels of the tables, how they read entities and value objects
tests/Acceptance/Expect         assertions (PHPUnit's need its runner to describe a failure)
tests/Double/                   the ports' test implementations
tests/Domain/                   PHPUnit: value objects rich in edge cases, intents refused exactly when not offered
tests/Application/              PHPUnit: the decorators of the handlers: the translation of the refusals of the domain (UseCaseRefused,
                                RefusalTranslating…Handler), the unit of work they begin and commit (Transactional…Handler)
tests/Architecture/             PHPUnit: no bounded context uses another one but its Contract, a Contract imports nothing,
                                no domain class in a request or a response, every handler a CommandHandler, a
                                QueryHandler or an EventHandler, every event handler subscribed in the scenarios
tests/Mutation/                 the scenarios of each feature as a PHPUnit test, for the tests of mutation only
```

The scenarios do not know the command bus of the API: `Application::dispatch()` sends a command to its handler, and a query is called directly with the presenter of the core keeping its answer (`KeptOrganization`, ADR 0085), each through the decorators of its kind like the API, a command in its unit of work, then each of its reactions in its own (`SynchronousEvents::deliverAfter()`); a scenario reads the response the method of `Application` gives back. Every event handler of the core, the translators publishing the integration events included (ADR 0046), reacts in the scenarios as in the API (`Application::translators()` and `reactions()`; `tests/Architecture/EventHandlersSubscribedTest` fails when one is missing): a scenario checks the side effects of a gesture in the other contexts, never the events themselves, but for a rule on their delivery or a published event, the contract of a context (the facts of Prospecting and of PersonalData, `publier-les-faits-de-prospecting.feature`, `publier-les-faits-de-personaldata.feature`): how many are published (`SynchronousEvents::published()`), a reaction delivered again (`Application::publishAgain()`, `arreter-de-prospecter.feature`); it may add a reaction of its own after them (`Application::alsoReactWith()`, `FailingReaction` in `une-commande-ecrit-tout-ou-rien.feature`, writing before it throws, its event in the failures); the intents tests check that an accepted intention records its event. The services the contexts publish (ADR 0045, 0089, `Contract/Service`) are asked through `Application::consultMembers()`, `whichAreContacts()`, `whichAreProspected()`, `listOrganizationFacts()`, `listExchangeFacts()`, `listContactFacts()` and `listAccounts()`, as the anticorruption layers ask them, in `features/langage-publie.feature`. `Application` plays the client: it gives the identities of what is created (`newIdentity()`, time ordered UUIDs from `TimeOrderedUuids`) and the moment of the commands (`now()`, set by `nous sommes le "2026-10-20 14:00"`); a refusal is the `UseCaseRefused` of the last call (`refusal()`).

## Adding or changing a rule

1. Write the scenario in the feature of the intent (one feature per use case, named after it in French: `demenager.feature` for `Relocate`), with the words already used (`Vocabulary` lists the table labels). Run `make test-core`: it must fail, and for the expected reason.
2. Missing step: Behat prints a snippet; add it to the context of the domain (`OrganizationContext`, `AccountContext`, `PersonalDataContext`) or to `ScenarioContext` for shared ones. Steps arrange data through the aggregates and repositories (and save what they change), act through `Application`, assert on responses or on the stored state.
3. A new port gets a working double in `tests/Double`, behaving like its real adapter.
4. Make it pass in `src`, then refactor with the scenarios green.
5. `make test-core && make lint`, then `make test` (the API uses the core).

Check that a scenario really protects its rule: break the rule in `src`, the scenario must fail, then restore it; `make mutation` does it for every line the branch adds ([below](#tests-of-mutation)).

## Tests of the API

- `tests/Api`: functional tests through `Base/ApiTestCase`, whose `login()` signs a member in for real on the user pool `prospecter-test` of MiniStack (`AccessTokenTest`, `SignInTest`). The tables of the prefix `prospecter-test` and the user pool are recreated for each test, with the data and the members of the demonstration, in the MiniStack of the tests (`ministack-test`, one per checkout, without port, state or Lambdas, never that of the stack: `make test-api` starts it, ADR 0109); the tests run in four processes with ParaTest (`TEST_PROCESSES=`), each on its own tables and user pool (`TEST_TOKEN` in `.env.test`: `prospecter-test1`…); host `api.test.prospecter.io`; variables in `.env.test`.
- `tests/Shared/Messaging/EventCodecTest`: every event class of the core is listed and survives a round trip through JSON, under the source of its context; `SynchronousDeliveryTest`: an event published by a reaction inherits its cause one level deeper, the events of one command share its correlation, two reactions answering each other stop beyond `EventLoop::MAX_EVENT_DEPTH`; `tests/Architecture/ReactionsAreSubscribedTest`: every event handler of the core is a translator or a subscription of `config/subscriptions.json`, which names only known reactions and events, a domain event subscribed to in its own context only.
- `tests/Shared/DynamoUnitOfWorkTest`: the unit of work on the tables of MiniStack (levels, one write per item, two additions to an item summed, a put replacing another keeping its condition on the item as stored, the ceiling of 100, the refusal carried by a write, what a read sees before the commit); `tests/Api/AllOrNothingApiTest`, with the delivery `sync`: a reaction refusing or failing (`Tests\App\Double\FailingReaction`, a subscription of the tests armed by the test, the client not rebooted) leaves the tables as they were, and an email taken meanwhile by another request (`Tests\App\Double\EmailTakenMeanwhile`) is refused at the commit, translated like any refusal.
- The outbox (ADR 0098): `tests/Shared/CommitOutboxTest` (one item at the outermost commit, a commit publishing in two contexts refused, none without event, a discarded unit throwing its events away, none for a unit refused at its commit after its events were delivered, the ceiling of an item), `tests/Api/CommitOutboxApiTest` (a command with `INTEGRATION_EVENTS_DELIVERY=outbox`, set by `Base/DeliversThroughTheOutbox`, which rebuilds the services of the kernel for a command of the console: one item with its domain and integration events, expiring a week later), `tests/SignIn/{OpenAccountCommandTest,RegisterMemberCommandTest}` (a gesture of the console commits in Accounts alone, ADR 0100), `tests/Shared/TablesTest` (the stream and the TTL of the tables); the bus is `Tests\App\Double\InMemoryEventBridge`, the handler of the client of the SDK in the tests, keeping each `PutEvents` and failing entries when asked: `OutboxRelayTest` (ten entries per put, a partial failure failing the batch), `RepublishOutboxCommandTest`.
- The worker (ADR 0101, 0102, 0104): `tests/Shared/Messaging/IntegrationEventConsumerTest` gives `IntegrationEventConsumer` invocations in the shape of the input transformer, internal and between contexts, with the delivery `outbox`: what a reaction publishes one level deeper in its outbox, an event delivered twice applied once, the inbox in the table of the context of the subscription, two subscriptions to one event not replaying each other, a refusal, an event too deep, an unknown subscription or an unreadable event put in the failures without a retry, a refusal logged with its `eventId`, its correlation, its `reason` and its `field` (`Tests\App\Double\InMemoryLogger`), a failure thrown writing nothing, not even the inbox; `tests/Shared/RedriveIntegrationFailuresCommandTest` the redrive. SQS and Lambda are `Tests\App\Double\InMemorySqs` and `InMemoryLambda`, the handlers of the clients of the SDK in the tests. The rules of the bus, the retries of Lambda and its destination are tried on an instance on AWS: MiniStack does not run them from a rule. A conflict is applied again three times at most, then thrown; a subscription naming a handler per event gives each its own; an event it does not listen to is refused.
- `tests/<Context>`: the adapters on their real table or service (`DynamoPersonRepositoryTest`: the reservation refuses an email taken meanwhile; `DynamoOrganizationFactsRetrieverTest`, `DynamoExchangeFactsRetrieverTest`, `DynamoContactFactsRetrieverTest`: the revision of each save, the facts as the unit of work is about to write them, absent once removed, none for the profile of a member, those of an account by slice; `DynamoAccountListRetrieverTest`: the accounts by slice, the keys written again; `OrganizationSearchTest`: found by the beginning of the name or of the email, the keys written again; `GeoplateformeGeoLocationTest`; `SignIn/RsaPublicKeyTest`); `tests/Architecture`: the boundaries (contexts, domain behind the application, one table per context); `tests/Local`: what only the local stack has (the profiler, its CORS). A test failing because of a limit of MiniStack is skipped with its reason; a dev instance on AWS is the safety net.
- `tests/Reporting` (ADR 0104): `DynamoFactRepositoryTest` (an older revision ignored, a terminal fact winning and forgotten 15 days later, two recordings of one account at the same time both counting, a fact changed meanwhile cancelling the recording written from what was read, an exchange moved to another month, several facts in one unit), `RebuildFiguresCommandTest` (the figures of the demonstration counted again, the former version removed, nothing written but the table of Reporting, the number of accounts counted said, two, then none without failing), `FiguresFollowTheGesturesTest` (the figures follow the gestures of the API, with the delivery `sync`).
- `tests/Consistency` (ADR 0105): `CheckConsistencyCommandTest` runs `app:consistency:check` on the demonstration, its figures counted again: nothing to show, then each discrepancy written by hand in the tables (a figure, the exchanges of a month, no active version, a contact attached to no organization, a forgotten contact still attached, a member without profile, an account without member, an exchange of an organization no longer prospected, an account without the key of the list of the accounts, an exchange without the key listing it in its account) or a message in the failures of the worker or of the relay (`InMemorySqs` counts the messages waiting), shown with its account and its correction, `--account` alone, and the tables unchanged by the check.
- Unit tests extend PHPUnit's `TestCase` and use hand-written doubles (`tests/Double`), no mock library.
- PHPUnit 13: attributes only (`#[DataProvider]`, `#[Group]`), static data providers, abstract base classes named `*TestCase`.

## Tests of the storage

`tests/StorageTest`: the storage as the API and the browsers use it, on the bucket `prospecter-test-files` of the MiniStack of the tests (`ministack-test`, as for the API), recreated before each test; `tests/PrivateFilesTest` the private files, on `prospecter-test-private-files`, the test sending and reading as a browser.

## No service outside the stack

No test depends on a service outside the local stack: it doubles it, so that a red test always means a defect of Prospecter, never a failure of a third party (ADR 0092). The tests of the API give the geocoder an address of no host (`APP_GEOCODER_URL` of `.env.test`, `GeoplateformeGeoLocationTest` on a `MockHttpClient`); every request leaving the API is answered by the double `tests/Double/OutsideServices` (`framework.http_client.mock_response_factory`), empty unless a test makes the geocoder place an address (`DashboardApiTest`), never by an alias of a service of the framework; EventBridge its double in memory (`InMemoryEventBridge`).

## The journeys

- `make e2e`: Playwright on the running stack (`apps/front/e2e`), one journey at a time, the API asking the double of the geocoder of nginx meanwhile (`http://nginx:8081/search`, `docker/nginx/conf.d/geocoder-double.conf`): a known place (Strasbourg) at a fixed position, any other address not placed, as the service of the IGN answers; a double that does not answer stops the journeys before they start. Afterwards, whatever the result, and with `make start`, the API asks the IGN again. Before them, `make e2e` warms the relay and the worker (eight containers of the worker: a gesture has several reactions, its facts among them), then opens an account and registers a member by the console (`E2E_RUN`, the registration tried again until the worker wrote the founder): `console-gestures.spec.ts` signs each in, their member and profile written by the reactions; without `E2E_RUN` it is skipped.
- A journey takes its `test` from `e2e/fixtures.ts` (Biome refuses it from `@playwright/test`): the maps get their style from a double, without tiles, credited as the real one, and a journey whose pages ask a host outside the stack, by HTTP or WebSocket, fails, naming it (`outside-the-stack.spec.ts`). A service a journey needs is doubled by its own route (`page.route`, `context.route`), which wins: OpenStreetMap in `directions.spec.ts`, a resource of the API changed to the case of the journey.
- A journey needing a new place adds it to the map of the double.
- A journey passes whatever the data of the base: right after `make install` (the demonstration data only) as after other journeys ran. A journey comparing screenshots acts where its gesture changes the picture whatever the data: the map of a single organization is centered on its marker over the plain background of the double, so `mobile-zoom.spec.ts` pinches it off its center.

## Tests of mutation

What the tests of a branch protect (ADR 0091): a tool changes a line the branch adds (a mutant: a condition inverted, a call removed, a value changed) and runs the tests covering it; a mutant they let pass **survives**, a change the tests do not see.

- `make mutation`: the core then the front, on the lines added since `origin/dev`, committed or not, a new file once added to git (`BASE=` another reference); a project where the branch adds no line in `src` runs nothing. `make mutation-api`: the API, on demand (on MiniStack), minutes per mutant.
- **The core**: Infection on PHPUnit (`infection.json5`, `tests/Mutation/phpunit.xml.dist`), the unit tests and the scenarios together. Infection knows no Behat and mutates nothing a test of PHPUnit does not cover, the use cases included: `tests/Mutation/ScenariosTest` runs the scenarios of each feature in its process, PHPUnit recording the coverage of the test. Behat runs there with `--xdebug` (without it, Behat restarts PHP without Xdebug and the coverage is lost), its error handlers removed afterwards. One test per feature: Behat booted for each scenario would take too long. `make test-core` runs neither twice (`phpunit.xml.dist` leaves `tests/Mutation` out).
- **The API**: Infection on PHPUnit, 4 processes, each its own tables and user pool on the MiniStack of the tests (`TEST_TOKEN` in `.env.test`: `prospecter-test1`…, left in it); a line most tests cross is skipped (S) past the timeout.
- **The front**: Stryker with Vitest (`stryker.config.json`), per test coverage, on the ranges of the added lines (Stryker reads no git diff); neither the tests, the generated files nor the components of shadcn (`src/shared/ui`: class names no test reads).
- **Reading a survivor**: each one is killed by a test protecting the behaviour, or justified in the pull request: equivalent (a cast without effect, the same behaviour another way) or noise. No minimum score: equivalent mutants would make it arbitrary. Not in `make ci`: the first run of every test, with its coverage, takes minutes. Reports: `var/mutation.log` (core, API), `reports/mutation.json` (front).
