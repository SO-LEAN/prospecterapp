# The MCP server

What is in force; the reasons are in the records it names (`docs/adr`), read only to know why or before changing it (ADR 0090).

An AI (Claude web, Claude Code, any client of the Model Context Protocol) reaches Prospecter as the member it signed in, with exactly their rights: the API serves an MCP server without session on `https://api.<domain>/mcp` (ADR 0156), and the AI signs the member in on Cognito through a facade of the API keeping nothing (ADR 0157). Status: the server runs, an AI reads through it everything its member reads on the screens (a tool per endpoint of reading, below), and the facade signs the AIs in (every step below); an access token of the SPA given by hand opens `/mcp` too; of the writes, an AI notes an exchange, once (ADR 0166), and manages the organizations and the contacts as on the screens, but their forgetting; the others come next.

```
AI (Claude)                         API (api.<domain>)                               Cognito
 1. POST /mcp, no token ──────────▶ 401 WWW-Authenticate: Bearer resource_metadata=…
 2. GET /.well-known/oauth-protected-resource/mcp ─▶ {resource: <api>/mcp, authorization_servers: [<api>]}
 3. GET /.well-known/oauth-authorization-server ───▶ endpoints, S256, CIMD, auth method none
 4. browser: GET /oauth/authorize ─▶ client checked (its metadata document), PKCE of the AI
                                     302 ───────────────────────────────────────────▶ sign-in page (hosted UI)
                                                                                      the member signs in
 5.                                  GET /oauth/callback?code=<Cognito>&state=<seal> ◀── 302
                                     302 to the AI: code=<seal of the request and of the code of Cognito>
 6. POST /oauth/token ─────────────▶ seal opened, verifier of the AI checked ─────────▶ code exchanged (client secret, PKCE of the API)
                                     ◀── the tokens of Cognito, as they are ◀──────────
 7. POST /mcp, Bearer <access token of Cognito> ─▶ firewall mcp: the member, their roles; the tool runs
 8. expired: POST /oauth/token grant_type=refresh_token ─▶ passed to Cognito
```

## The server

- `symfony/mcp-bundle` (Symfony AI) on `mcp/sdk`, both experimental, pinned at an exact version and moved by hand, their changelogs read. `session.store: none` came after the last tag of the bundle (`v1.0.0-BETA1`), on its `main` with `mcp/sdk` 0.10.0: the bundle is pinned at that commit (`dev-main#790442a8…` in `apps/api/composer.json`), `mcp/sdk` at `0.10.0`, until a tag carries it.
- One server, `prospecter` (`config/packages/mcp.yaml`), HTTP « streamable » on `/mcp` of the host of the API, `allowed_hosts` that host, in the Lambda of the API behind its HTTP API (`$default` on AWS, nginx locally): no infrastructure of its own.
- Without session: both eras of the protocol on the same endpoint, the SDK routing each request by its `params._meta`. The revision `2026-07-28` has no handshake and no session; the clients of the `initialize` handshake (`2025-11-25` and before) are answered without `Mcp-Session-Id`, each request in a session of its own thrown away after it, `GET` and `DELETE` 405, without the requests of the server (elicitation, sampling), the subscriptions and the logging, which no tool needs.
- Its rate, as that of the public routes of the facade, limited as the other public routes of the API: by address by the edge of the installation, and by the throttling of the HTTP API on routes of their own, added with them (the stage throttles nothing today, and throttling `$default` would cap the whole API).
- No CORS: `/mcp` is called by servers (Claude web) and native clients (Claude Code), never by a page.

## Who calls

- The firewall `mcp` (`^/mcp$`, stateless) checks the access tokens of Cognito as the firewall `api` does (`Security\AccessTokenHandler`, `auth.md`), those of the client `prospecter-mcp` beside those of the SPA (the service `app.mcp_token_handler`, `UserPool::CLIENT_NAMES_OF_THE_MCP_SERVER`), and loads the same `App\Security\User`: an AI does what its member may, reads the personal data in clear or masked as they do, no scope of its own.
- Without a token: 401 `WWW-Authenticate: Bearer resource_metadata="<api>/.well-known/oauth-protected-resource/mcp"` (the entry point); a token refused (expired, of another pool or client, an id token) adds `error="invalid_token"` (RFC 6750) (the failure handler of the authenticator); both `Security\McpAuthenticationEntryPoint`, naming the metadata by `SignIn\OAuth\ProtectedResource`. Claude starts its sign-in only on a 401, never on a tool answering an error.

## Every endpoint has its tool

- Every endpoint a member calls, a route whose controller declares `#[IsGranted]`, has its tool (ADR 0163): an AI reads and does what its member reads and does on the screens, and the server never lags behind the application. The public routes (the facade below, the public booking page, the push of Gmail, the user pool, the documentation) are no endpoints of a member.
- But two lists, in `tests/Architecture/EveryEndpointHasItsToolTest`, which fails naming each endpoint of a member without a tool and on neither: `NEVER`, kept on the screen: the forgetting of a contact (GDPR, `api_contacts_forget`), the credentials of the sign-in (`api_me_sign_in`, `api_me_change_login_email`, `api_me_change_password`), the connection of a connector, its consent given to Google in a browser (`api_me_connections_google_authorize`, `api_me_connections_google_connect`, `api_me_connections_google_import_gmail`), and the members and their roles when they have endpoints; `TO_COVER`, the writes, which the tickets after the reads cover, the last of them removing it. The same test checks that a tool adapting a `GET` carries `readOnlyHint`, that a tool of a write says whether its AI asks its member first and whether it reaches outside Prospecter (below), that no tool adapts an endpoint of `NEVER`, that no route a tool adapts waits in `TO_COVER`, and that every route named by `#[Adapts]` or a list exists.

## Writing a tool

- One tool per endpoint, `src/<Context>/Mcp/<Intent>Tool.php` beside its controller (`Prospecting\Mcp\SearchOrganizationsTool` beside `Prospecting\Controller\SearchOrganizationsController`), a `final readonly` service carrying `#[Adapts('<the name of the route>')]` (`Shared\Mcp\Adapts`) and `#[McpTool]` on `__invoke` (name in French kebab-case, a description for the AI in English, `annotations: new ToolAnnotations(readOnlyHint: true)` for a reading; for a write `readOnlyHint: false` and `destructiveHint`, `true` for a tool adapting a `DELETE`, which removes or erases: its AI asks its member before calling it; `false` for any other, the protocol taking a write for destructive unless it says otherwise; and `openWorldHint`, `true` only for a tool reaching outside Prospecter (`changer-logo-organisation`), `false` for the others, the protocol taking a tool for reaching outside unless it says otherwise; the tools of reading do not say it yet), its arguments those of the route and of the query of the endpoint (`id`, `q`, `after`, `from`, `to`, `timeZone`…, each described by its `@param`), its namespace listed in the `registry` of the server (`config/packages/mcp.yaml`).
- It does what its controller does, in its order: reads the resource of the route by its resolver (`OrganizationResolver::read()`, `ExchangeResolver`, `CampaignResolver`, `ToDoResolver`: an unknown one refused by the core), then checks the attributes `#[IsGranted]` of the controller by `Security\ToolAccess::denyUnlessGranted()` (the role, the voter of the resource, `User::PERSONAL_DATA`), builds the input of the endpoint from its arguments and checks it (`Shared\Mcp\ToolInputs`: `valid()`, or `mapped()` denormalizing as the query string is, its dates included), and calls the same reader, query or command of the core as the controller: what a controller composed inline goes to a reader both share (`Contacts\ContactSearchReader`, `Dashboard\DashboardReader`, `Exchanges\AttachmentDownloads`…), never composed twice; the command an endpoint composes from a large input, that input builds it for both (`StartProspectingInput::commandOf()`, `CollectContactInput::commandOf()`). The tools writing an organization share what each does as its controller, `Prospecting\Mcp\OrganizationWrites::write()`: the organization read, the access checked (the role, the voter, the other attributes given), the input checked, the command built by the tool dispatched, the organization answered as `lire-organisation` reads it.
- An image (the logo of an organization) is given by its address on the web, which the API downloads (ADR 0168): `Shared\Mcp\ImageAddressInput` (`url`, http or https) and `Shared\Mcp\ImagesOnTheWeb::whileDownloaded()`, once the member checked, never on a private network (`app.images_on_the_web_http`, a `NoPrivateNetworkHttpClient`), 5 seconds at most, no redirect followed, 2 MB at most, then checked as the image of the screen (`Shared\Images`: 2 MB, JPEG, PNG or WebP); an address out of reach a violation of `url`, an image refused the violations of the screen, 422; the file removed once the command used it, within the call (a kernel per request under FPM: no reset of the services to count on). Such a tool says `openWorldHint`.
- It answers the resource of the endpoint by `Shared\Mcp\ToolResults::of()`, serialized as the controller serializes it, its links (`_links`) included, for the AI to follow them from one resource to another, with the tool of the endpoint each link names. But a tool noting an exchange (ADR 0166): `Exchanges\NotedOnceAnswers` answers `{status, exchange, erasedBy, erasedAt}` (`Exchanges\Resource\NotingResource`), `noted` with the exchange as `lire-echange` reads it, `alreadyNoted` with the exchange noted first (without it when both were noted at once, `ExchangeNotedMeanwhile`), `erasedBefore` with the member who erased it, named as the authors of an exchange, and when; it notes with `noteOnce`, so that the core refuses what was noted before, by an AI, the import of Gmail or a member.
- A refusal is the error of the tool (`isError`), but « already noted », « noted meanwhile » and « erased before » of a tool noting an exchange, its result (above, ADR 0166), its text the problem+json the endpoint answers: `Shared\Mcp\RefusingTools` runs the tools (set on the builder of the server by `Shared\DependencyInjection\RefusingToolsPass`) and translates a refusal of the core (`Shared\RefusalProblems`, as `UseCaseExceptionListener`), an access denied (`Security\AccessProblems`, as `ApiAccessDeniedHandler`: `roleNotAllowed` 403, `unknown<Resource>` 404 for another account), a service out of reach (`Shared\UnavailabilityProblems`, as `ServiceUnavailableListener`: `directoryUnreachable`, `googleUnreachable`, `secretsUnavailable` 503) and the violations of the arguments (422); any other exception stays a failure of the server. A refusal reaches the AI as the SPA gets it, its `reason`, its `context` and its `detail` in English (ADR 0073): the AI words it for its member, in their language. The pass reads the locator of the tools the bundle gives the builder (`setContainer`) and sets its runner (`setReferenceHandler`): an app of the bundle (`#[AsMcpApp]`), whose pass sets a runner of its own, would need both composed.
- The tools: `qui-suis-je` (`Me\Mcp\WhoAmITool`, no endpoint), the member served, as `/api/me` reads them, their account, and whether they read the personal data in clear (`readsPersonalData`, the role `ROLE_PERSONAL_DATA`); then one per endpoint of reading: `rechercher-organisations`, `lire-organisation`, `chercher-etablissements`, `lire-echanges-contact`, `lire-echanges-a-venir-contact`, `proposer-lieu-de-rendez-vous`, `rechercher-contacts`, `rechercher-contacts-par-tags`, `lire-contact`, `lire-organisations-du-contact`, `lire-organisation-proposee`, `lire-contacts-organisation`, `lire-echanges-organisation`, `lire-echanges-a-venir-organisation`, `lire-echanges-a-mettre-en-conformite`, `reconnaitre-appelant`, `lire-agenda`, `lire-ma-journee`, `lire-echanges-a-traiter`, `lire-echanges-qui-chevauchent`, `lire-echange`, `telecharger-piece-jointe`, `lire-synchronisation-google`, `lire-mes-connexions`, `lire-client-google`, `lire-mes-a-faire`, `lire-a-faire`, `lire-a-faire-contact`, `lire-a-faire-organisation`, `lire-tags-contact`, `lire-tags-organisation`, `lire-tags-proposes`, `lister-campagnes`, `lire-campagne`, `lire-destinataires-campagne`, `lire-message-campagne`, `lire-tableau-de-bord`, `lire-mon-compte`, `lire-mes-rappels`, `lire-ma-page-de-reservation`; of the writes, `noter-un-echange` and `noter-un-echange-organisation` (`idempotentHint`), with the `Message-ID` of an e-mail or the conversation of a LinkedIn message they were read in; on the organizations `prospecter-organisation`, `reviser-identite-organisation`, `changer-logo-organisation` (below), `changer-coordonnees-organisation`, `demenager-organisation`, `ecrire-observations-organisation`, `rattacher-a-holding`, `ajouter-contact-organisation` (a contact to attach among them), and, destructive, `arreter-prospection` (answering nothing, as its endpoint), `detacher-de-holding`, `retirer-logo-organisation`, `retirer-contact-organisation`, `ecarter-doublon-possible`; on the contacts `collecter-contact`, `renommer-contact`, `changer-civilite-contact`, `changer-fonction-contact`, `changer-coordonnees-contact` (their profile on LinkedIn among their links); the route each adapts is its `#[Adapts]`.
- Its tests: `tests/Api/ReadingToolsApiTest` calls each tool and its endpoint as a prospector, an assistant without the right on the personal data, an administrator, a member who is no prospector and a member of another account, and asserts the same answer, the resource or its problem (a test keeping its kernel for a double, `keepTheKernel()`, sets the frozen clock of the tokens a minute later); `tests/Api/NotingToolsApiTest` notes an exchange by each tool, again, and once erased, and compares the refusals of each tool with those of its endpoint for an assistant, a member who is no prospector and a member of another account; `tests/Api/OrganizationAndContactToolsApiTest` calls each tool writing an organization or a contact as each of those five members, a refusal compared with that of its endpoint, a write done by a member its endpoint allows and answered as the screen then reads the resource (its link `self`), and lists the destructive ones as an AI does; `tests/Api/SignInOfTheAIsApiTest` signs an AI in through the facade on the Cognito of MiniStack, its sign-in page posted as a browser does, then calls `qui-suis-je` (and every refusal of the facade, the refresh and the sign-outs; the metadata documents of Claude doubled by `Tests\App\Double\ClientsOfTheAIs`, their hosts resolved by it); `tests/Api/McpApiTest` calls the tools in each era (a `tools/call` carrying the revision in its `_meta`; `initialize` then `tools/call`, no `Mcp-Session-Id`), with a member of each right, and without or with a refused token; `tests/Api/ProtectedResourceApiTest` the metadata.

## The sign-in of the AIs

Cognito is the authority, but cannot be the authorization server Claude expects by itself: no Client ID Metadata Document nor dynamic registration, no `code_challenge_methods_supported` in its discovery, no `resource` (RFC 8707) in its authorization code. The facade of the API fills those gaps and keeps nothing (`src/SignIn/OAuth`):

- `GET /.well-known/oauth-protected-resource/mcp` (and without `/mcp`, RFC 9728; `SignIn\Controller\ShowProtectedResourceController`, public, out of the contract of the API): `resource` `<api>/mcp` exactly as the member types it in Claude, `authorization_servers` the API alone (Claude reads the first only).
- `GET /.well-known/oauth-authorization-server` (RFC 8414, `SignIn\Controller\ShowAuthorizationServerController`, `SignIn\OAuth\AuthorizationServer`): its endpoints, `response_types_supported: [code]`, `grant_types_supported: [authorization_code, refresh_token]`, `code_challenge_methods_supported: [S256]`, `token_endpoint_auth_methods_supported: [none]`, `client_id_metadata_document_supported: true` (with `none`, the condition of Claude to use it), no `registration_endpoint`.
- `GET /oauth/authorize` (`AuthorizeController`): the client is its Client ID Metadata Document (`OAuth\ClientMetadataDocuments`), an HTTPS URL fetched (its host on no private network, the client `NoPrivateNetworkHttpClient` of Symfony refusing it, 5 s, 5 kB, no redirect followed), its `client_id` equal to its URL, the `redirect_uri` among its `redirect_uris` (`OAuth\ClientMetadata`), a loopback address matched without its port (Claude Code declares `http://localhost/callback` and `http://127.0.0.1/callback`). An invalid client or redirect: 400 `application/problem+json`, its `reason` `unknownClient` (`OAuth\UnknownClientListener`), never a redirect to an address not checked. Then, the redirect checked, what the AI got wrong sends it back with its error: `response_type` other than `code` (`unsupported_response_type`), `code_challenge` S256 missing (`invalid_request`), `resource` other than `<api>/mcp` when given (`invalid_target`). Otherwise a redirect to the sign-in page of Cognito (`OAuth\CognitoSignIn`, `COGNITO_SIGN_IN_URL`) with the client `prospecter-mcp`, a PKCE of the API (`OAuth\Pkce`) and, as `state`, the request sealed for 15 minutes.
- `GET /oauth/callback` (`ComeBackFromCognitoController`): Cognito comes back with its code; a redirect to the AI with its `state` and, as `code`, the request and the code of Cognito sealed (5 minutes); with the `error` of Cognito when the member did not sign in; a `state` the facade did not seal, a 400 leading nowhere.
- `POST /oauth/token` (`IssueTokensController`, `application/x-www-form-urlencoded`): `authorization_code`, the seal opened, the verifier of the AI checked against its challenge, the same client and redirect, then the code of Cognito exchanged with the secret of `prospecter-mcp` (read from Cognito by `UserPool::mcpClientSecret()`, cached) and the verifier of the API at its token endpoint (`OAuth\CognitoTokens`, `COGNITO_OAUTH_URL`), the tokens of Cognito answered as they are; `refresh_token`, passed to Cognito. Every refusal `invalid_grant`, another grant `unsupported_grant_type` (RFC 6749, `OAuth\GrantRefusedListener`). The protocol imposes two exceptions to one intent per endpoint (ADR 0025): `/oauth/token` carries two by its `grant_type`, `/oauth/authorize` and `/oauth/callback` only redirect.
- Nothing kept: the request travels sealed (`OAuth\Seal`, `sodium_crypto_secretbox`, its key `OAUTH_SEAL_KEY` a secret of the API, sealed for one purpose and a while, `OAuth\SealPurpose`), in the `state` given to Cognito then in the code given to the AI; Cognito refusing its code a second time, the code of the facade serves once. No table, no item, nothing in the core.
- Claude web identifies itself by the document Anthropic publishes, its redirect `https://claude.ai/api/mcp/auth_callback`; Claude Code by its own (`https://claude.ai/oauth/claude-code-client-metadata`), on a loopback port of the session. Neither needs anything configured.
- A global sign-out revokes the refresh tokens of every client of the member, their AIs included: the SPA signs out by revoking its own refresh token only (`RevokeToken`), a global sign-out kept for « Se déconnecter partout » in the menu of the account. An access token stays valid until it expires (1 h), as for the SPA (`auth.md`).

## Trying it

- The spike #202 proved the server on a throwaway branch, before it was built: in the Lambda on MiniStack, a `tools/call` of the revision `2026-07-28` (its `_meta` carrying `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities`, the headers `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name`), then `initialize` and `tools/call` of `2025-11-25` answered without `Mcp-Session-Id`, `GET` 405, a token refused 401, and the MCP Inspector.
- The metadata name the API by `APP_API_HOST`, without the port a worktree serves its stack on: a client following them locally needs the stack of the main checkout, on 443.
- Locally, the facade: the stack of the main checkout, `GET https://api.prospecter.localhost/oauth/authorize?response_type=code&client_id=<a metadata document reachable in https>&redirect_uri=<one it declares>&code_challenge=<S256>&code_challenge_method=S256&state=…` in a browser, the sign-in page of MiniStack (a member of the demonstration), then the code exchanged by `curl -d grant_type=authorization_code -d code=… -d client_id=… -d redirect_uri=… -d code_verifier=… https://api.prospecter.localhost/oauth/token`.
- Locally, the server: `curl` with a token of a member of the demonstration (`Authorization: Bearer`, the access token the SPA sends, read in the network panel of the browser), in each era (a `tools/call` carrying in `params._meta` the revision `2026-07-28`; `initialize` then `tools/call`), and the MCP Inspector (`npx @modelcontextprotocol/inspector --cli <url> --transport http --header "Authorization: Bearer …" --method tools/list`).
- Claude Code and Claude web need an instance reachable from Anthropic:
- Claude Code: `claude mcp add --transport http prospecter https://api.<domain>/mcp`, then `/mcp` to sign in.
- Claude web: Customize › Connectors › Add custom connector, the URL `https://api.<domain>/mcp`, nothing else: an instance reachable from the egress of Anthropic (`160.79.104.0/21`), which the local stack is not.
