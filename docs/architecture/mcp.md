# The MCP server

What is in force; the reasons are in the records it names (`docs/adr`), read only to know why or before changing it (ADR 0090).

An AI (Claude web, Claude Code, any client of the Model Context Protocol) reaches Prospecter as the member it signed in, with exactly their rights: the API serves an MCP server without session on `https://api.<domain>/mcp` (ADR 0156), and the AI signs the member in on Cognito through a facade of the API keeping nothing (ADR 0157). Status: the server runs, an AI reads through it everything its member reads on the screens (a tool per endpoint of reading, below) and identifies who Prospecter knows before creating anything (ADR 0173), then records a contact and their organization in one call (ADR 0177), and the facade signs the AIs in (every step below); an access token of the SPA given by hand opens `/mcp` too; of the writes, an AI notes an exchange, once (ADR 0166), manages the organizations and the contacts as on the screens, but their forgetting, plans, handles, corrects and erases the exchanges, joins files to them by their address on the web (ADR 0172), manages the to-dos, the tags, the campaigns, which it leads too, sending each message itself (ADR 0186), the booking page, the reminders and the profile of its member, checks their connections and catches up their e-mails of Gmail; what is kept on the screen is listed below.

```
AI (Claude)                         API (api.<domain>)                               Cognito
 1. POST /mcp, no token ──────────▶ 401 WWW-Authenticate: Bearer resource_metadata=…
 2. GET /.well-known/oauth-protected-resource/mcp ─▶ {resource: <api>/mcp, authorization_servers: [<api>]}
 3. GET /.well-known/oauth-authorization-server ───▶ endpoints, S256, CIMD, auth method none
 4. browser: GET /oauth/authorize ─▶ client checked (its metadata document), PKCE of the AI
                                     302 ───────────────────────────────────────────▶ sign-in page (hosted UI)
                                                                                      the member signs in
 5.                                  GET /oauth/callback?code=<Cognito>&state=<seal> ◀── 302
                                     302 to the AI: code=<seal of the request and of the code of Cognito>
 6. POST /oauth/token ─────────────▶ seal opened, verifier of the AI checked ─────────▶ code exchanged (client secret, PKCE of the API)
                                     ◀── the tokens of Cognito, as they are ◀──────────
 7. POST /mcp, Bearer <access token of Cognito> ─▶ firewall mcp: the member, their roles; the tool runs
 8. expired: POST /oauth/token grant_type=refresh_token ─▶ passed to Cognito
```

## The server

- `symfony/mcp-bundle` (Symfony AI) on `mcp/sdk`, both experimental, pinned at an exact version and moved by hand, their changelogs read. `session.store: none` came after the last tag of the bundle (`v1.0.0-BETA1`), on its `main` with `mcp/sdk` 0.10.0: the bundle is pinned at that commit (`dev-main#790442a8…` in `apps/api/composer.json`), `mcp/sdk` at `0.10.0`, until a tag carries it.
- One server, `prospecter` (`config/packages/mcp.yaml`), HTTP « streamable » on `/mcp` of the host of the API, `allowed_hosts` that host, in the Lambda of the API behind its HTTP API (`$default` on AWS, nginx locally): no infrastructure of its own.
- Without session: both eras of the protocol on the same endpoint, the SDK routing each request by its `params._meta`. The revision `2026-07-28` has no handshake and no session; the clients of the `initialize` handshake (`2025-11-25` and before) are answered without `Mcp-Session-Id`, each request in a session of its own thrown away after it, `GET` and `DELETE` 405, without the requests of the server (elicitation, sampling), the subscriptions and the logging, which no tool needs.
- Its rate, as that of the public routes of the facade, limited as the other public routes of the API: by address by the edge of the installation, and by the throttling of the HTTP API on routes of their own, added with them (the stage throttles nothing today, and throttling `$default` would cap the whole API).
- No CORS: `/mcp` is called by servers (Claude web) and native clients (Claude Code), never by a page.

## Who calls

- The firewall `mcp` (`^/mcp$`, stateless) checks the access tokens of Cognito as the firewall `api` does (`Security\AccessTokenHandler`, `auth.md`), those of the client `prospecter-mcp` beside those of the SPA (the service `app.mcp_token_handler`, `UserPool::CLIENT_NAMES_OF_THE_MCP_SERVER`), and loads the same `App\Security\User`: an AI does what its member may, reads the personal data in clear or masked as they do, no scope of its own.
- Without a token: 401 `WWW-Authenticate: Bearer resource_metadata="<api>/.well-known/oauth-protected-resource/mcp"` (the entry point); a token refused (expired, of another pool or client, an id token) adds `error="invalid_token"` (RFC 6750) (the failure handler of the authenticator); both `Security\McpAuthenticationEntryPoint`, naming the metadata by `SignIn\OAuth\ProtectedResource`. Claude starts its sign-in only on a 401, never on a tool answering an error.

## Every endpoint has its tool

- Every endpoint a member calls, a route whose controller declares `#[IsGranted]`, has its tool (ADR 0163): an AI reads and does what its member reads and does on the screens, and the server never lags behind the application. The public routes (the facade below, the public booking page, the push of Gmail, the user pool, the documentation) are no endpoints of a member.
- But two lists, in `tests/Architecture/EveryEndpointHasItsToolTest`, which fails naming each endpoint of a member without a tool and on neither: `NEVER`, kept on the screen: the forgetting of a contact (GDPR, `api_contacts_forget`), the credentials of the sign-in (`api_me_sign_in`, `api_me_change_login_email`, `api_me_change_password`), the connection of a connector, its consent given to Google in a browser (`api_me_connections_google_authorize`, `api_me_connections_google_connect`, `api_me_connections_google_import_gmail`), and its disconnection, which an AI could not take back without that consent (`api_me_connections_google_disconnect`, `api_me_connections_google_stop_gmail_import`), the client of Google of the account and its notifications of Gmail, its credentials (`api_me_configure_google_client`, `api_me_remove_google_client`, `api_me_configure_gmail_notifications`, `api_me_remove_gmail_notifications`), the identity, the address and the logo of the organization of the account (`api_me_revise_organization_identity`, `api_me_relocate_organization`, `api_me_change_organization_logo`) (those three kinds, ADR 0183), the form of an upload (`api_uploads_prepare`, the tool joining a file preparing its own, ADR 0172), and the members and their roles when they have endpoints. The same test checks that a tool adapting a `GET` carries `readOnlyHint`, that a tool of a write says whether its AI asks its member first (a `DELETE`, or a write of `NEVER_TAKEN_BACK`: the cancellation of an exchange, the stopping of a campaign, the dismissal of a recipient) and whether it reaches outside Prospecter (below), that no tool adapts an endpoint of `NEVER`, and that every route named by `#[Adapts]` or a list exists.

## Writing a tool

- One tool per endpoint, `src/<Context>/Mcp/<Intent>Tool.php` beside its controller (`Prospecting\Mcp\SearchOrganizationsTool` beside `Prospecting\Controller\SearchOrganizationsController`), a `final readonly` service carrying `#[Adapts('<the name of the route>')]` (`Shared\Mcp\Adapts`) and `#[McpTool]` on `__invoke` (name in French kebab-case, a description for the AI in English, `annotations: new ToolAnnotations(readOnlyHint: true)` for a reading; for a write `readOnlyHint: false` and `destructiveHint`, `true` for a tool adapting a `DELETE`, which removes or erases, or a write nothing takes back (`annuler-echange`, listed in `NEVER_TAKEN_BACK`): its AI asks its member before calling it; `false` for any other, the protocol taking a write for destructive unless it says otherwise; and `openWorldHint`, `true` only for a tool reaching outside Prospecter (`changer-logo-organisation`, `changer-ma-photo`, `joindre-piece-jointe`, `relancer-synchronisation-google`, `relancer-synchronisations-google-echouees`, `verifier-mes-connexions`, `rattraper-gmail-contact`, `rattraper-gmail-organisation`; a planning pushed to Google by a reaction after it is not), `false` for the others, the protocol taking a tool for reaching outside unless it says otherwise; the tools of reading do not say it yet), its arguments those of the route and of the query of the endpoint (`id`, `q`, `after`, `from`, `to`, `timeZone`…, each described by its `@param`), its namespace listed in the `registry` of the server (`config/packages/mcp.yaml`).
- It does what its controller does, in its order: reads the resource of the route by its resolver (`OrganizationResolver::read()`, `ExchangeResolver`, `CampaignResolver`, `ToDoResolver`: an unknown one refused by the core), then checks the attributes `#[IsGranted]` of the controller by `Security\ToolAccess::denyUnlessGranted()` (the role, the voter of the resource, `User::PERSONAL_DATA`), builds the input of the endpoint from its arguments and checks it (`Shared\Mcp\ToolInputs`: `valid()`, or `mapped()` denormalizing as the query string is, its dates included), and calls the same reader, query or command of the core as the controller: what a controller composed inline goes to a reader both share (`Contacts\ContactSearchReader`, `Dashboard\DashboardReader`, `Exchanges\AttachmentDownloads`…), never composed twice; the command an endpoint composes from a large input, that input builds it for both (`StartProspectingInput::commandOf()`, `CollectContactInput::commandOf()`). The tools writing an organization share what each does as its controller, `Prospecting\Mcp\OrganizationWrites::write()`: the organization read, the access checked (the role, the voter, the other attributes given), the input checked, the command built by the tool dispatched, the organization answered as `lire-organisation` reads it. Those writing an exchange share `Exchanges\Mcp\ExchangeWrites` likewise (`write()`, `dispatched()` for those answering otherwise, `answer()` with the moment it was moved from for `deplacer-echange`), those writing a to-do `ToDos\Mcp\ToDoWrites` (the right to manage the personal data always checked), those writing a campaign `Campaigning\Mcp\CampaignWrites` (the campaign read by `CampaignResolver`, its voter and the right to manage the personal data checked; `dispatched()` for those answering nothing), the booking page of the member `Booking\Mcp\BookingPageWrites` and their profile `Me\Mcp\MyProfileWrites` (any member, their own; `writable()` checks them before a picture is downloaded). The command preparing or revising a campaign, `CampaignInput` builds it for its endpoint and its tool (`preparationOf()`, `revisionOf()`).
- A tool creating an organization, a contact or an exchange says an AI creates it (ADR 0185): `byAnAI: true` on its command (`noter-un-echange`, `noter-un-echange-organisation`, `noter-l-envoi`, `planifier-echange`, `planifier-echange-organisation`), or the command of the input built for an AI (`StartProspectingInput::commandOfAnAI()`, `CollectContactInput::commandOfAnAI()`: `prospecter-organisation`, `collecter-contact`, `enregistrer-un-contact`); the controllers never. What it creates reads `createdByAnAI` in its resource, and carries « MCP » on the screens; a new tool creating something does the same.
- A file (the logo of an organization, the picture of the member, a file joined to an exchange) is given by its address on the web, which the API downloads (ADR 0168, 0172): `Shared\Mcp\WebAddressInput` (`url`, http or https) and `Shared\Mcp\FilesOnTheWeb::whileDownloaded()`, once the member checked, never on a private network (`app.files_on_the_web_http`, a `NoPrivateNetworkHttpClient`), 5 seconds at most, no redirect followed, no heavier than the screen takes; an address out of reach a violation of `url`, said so when the file is behind a sign-in (401, 403) or its address redirects (a sign-in page perhaps): Prospecter signs in nowhere for its member; the file removed once the command used it, within the call (a kernel per request under FPM: no reset of the services to count on). An image is then checked as the image of the screen (`Shared\Mcp\ImagesOnTheWeb`, `Shared\Images`: 2 MB, JPEG, PNG or WebP), its violations 422. A file joined to an exchange (`joindre-piece-jointe`) is downloaded no heavier than the form of an upload the storage prepares (10 MB), sent with that form to the private bucket as a browser does (`Shared\UploadSender`, `Shared\UploadsSentByTheApi`, at `PRIVATE_UPLOADS_ENDPOINT` in place of the origin of the form: MiniStack locally, empty on AWS, the address of the form; the form whole, with its length, S3 refusing one sent in chunks, which MiniStack takes), then joined by the command of the endpoint; the bucket failing (5xx), limiting the requests (429) or out of reach, the private files are unavailable for now (`privateFilesUnavailable`, 503), any other refusal of the form a failure of the server. Such a tool says `openWorldHint`.
- It answers the resource of the endpoint by `Shared\Mcp\ToolResults::of()`, serialized as the controller serializes it, its links (`_links`) included, for the AI to follow them from one resource to another, with the tool of the endpoint each link names. But a tool noting an exchange (ADR 0166): `Exchanges\NotedOnceAnswers` answers `{status, exchange, erasedBy, erasedAt}` (`Exchanges\Resource\NotingResource`), `noted` with the exchange as `lire-echange` reads it, `alreadyNoted` with the exchange noted first (without it when both were noted at once, `ExchangeNotedMeanwhile`), `erasedBefore` with the member who erased it, named as the authors of an exchange, and when; it notes with `noteOnce`, so that the core refuses what was noted before, by an AI, the import of Gmail or a member.
- A refusal is the error of the tool (`isError`), but « already noted », « noted meanwhile » and « erased before » of a tool noting an exchange, its result (above, ADR 0166), its text the problem+json the endpoint answers: `Shared\Mcp\RefusingTools` runs the tools (set on the builder of the server by `Shared\DependencyInjection\RefusingToolsPass`) and translates a refusal of the core (`Shared\RefusalProblems`, as `UseCaseExceptionListener`), an access denied (`Security\AccessProblems`, as `ApiAccessDeniedHandler`: `roleNotAllowed` 403, `unknown<Resource>` 404 for another account), a service out of reach (`Shared\UnavailabilityProblems`, as `ServiceUnavailableListener`: `directoryUnreachable`, `googleUnreachable`, `secretsUnavailable`, `privateFilesUnavailable` 503, its cause logged at the level error, as Symfony logs it for the SPA) and the violations of the arguments (422); any other exception stays a failure of the server. A refusal reaches the AI as the SPA gets it, its `reason`, its `context` and its `detail` in English (ADR 0073): the AI words it for its member, in their language. The pass reads the locator of the tools the bundle gives the builder (`setContainer`) and sets its runner (`setReferenceHandler`): an app of the bundle (`#[AsMcpApp]`), whose pass sets a runner of its own, would need both composed.
- The tools: `qui-suis-je` (`Me\Mcp\WhoAmITool`, no endpoint), the member served, as `/api/me` reads them, their account, and whether they read the personal data in clear (`readsPersonalData`, the role `ROLE_PERSONAL_DATA`); ## The prompts

- A prompt of the protocol is a walk the AI offers its member (a command of Claude Code, an entry of Claude web): it chains the tools so that a sentence of the member, « synchronise mes contacts LinkedIn intéressants », is enough, nothing created nor noted twice. It reads nothing itself and writes nothing: its text is a message of the member to their AI, in French, each tool named as it is served; the tools check the access and refuse as they always do. Prospecter reads neither LinkedIn nor the mailbox for the AI: the AI reads them with its own tools (the extension of Claude for Chrome, the connector Gmail of Claude).
- `src/<Context>/Mcp/<Intent>Prompt.php` (`Identification`, `Campaigning`), a `final readonly` service with `#[McpPrompt]` on `__invoke` (name in French kebab-case, a title and a description in French for the member), its arguments strings described by their `@param` in French (a typed object is no argument of a prompt for the SDK, which skips it in the list: an argument of a few values is a string read into an enum, any other value an error of the protocol `-32602`, `RegistryException::invalidParams()`), its namespace listed in the `prompts` of the `registry` of the server (`config/packages/mcp.yaml`); it answers one message of the role `user`, its steps.
- `synchroniser-linkedin` (« Synchroniser LinkedIn », `SynchronizeLinkedInPrompt`; `what`, `contacts` or `messages`, `since`, optional): read LinkedIn since then, each person with their profile, names, job title, company and the page of the company; `identifier` by batches of a hundred, the member asked about each `toConfirm` and choosing the `new` that interest them; `enregistrer-un-contact`; for the messages, `noter-un-echange` (`noter-un-echange-organisation` for the page of a company) with `linkedInConversation` and `occurredAt` at its minute (the fingerprint of ADR 0166).
- `synchroniser-boite-e-mail` (« Synchroniser ma boîte e-mail », `SynchronizeMailboxPrompt`; `since`, optional): read the mailbox since then; `identifier` the correspondents, only those `known` kept but those the member asks to create, recorded by `enregistrer-un-contact`; `noter-un-echange` (or `noter-un-echange-organisation`) with the `messageId` of each e-mail, one sent to two contacts noted with each.
- Both, `since` not given, have the AI ask it first; end on a report (created, completed, already noted, ignored: `alreadyNoted` and `erasedBefore` counted already noted, so that a synchronization played again counts nothing created); and recall the rules: nothing `toConfirm` created without the answer of the member, nothing noted without its reference when the AI reads it, a refusal of Prospecter stopping the AI, which asks its member.
- `mener-une-campagne` (« Mener une campagne », `Campaigning\Mcp\LeadCampaignPrompt`, ADR 0186; `campagne`, its name or its id): find it by `lister-campagnes`; take `destinataire-suivant`; send the message by the tools of the AI, as is or adapted as its instruction says; note it by `noter-l-envoi` with the text really sent and its reference, already noted going on; dismiss whom it cannot reach by `ecarter-destinataire-campagne`, once the member confirmed; never send a second message to a recipient given again, stopping to say who (the import of the mailbox may note the sending first, ADR 0186); again until the campaign is no longer led, then a report.
- Their tests: `tests/Api/SynchronizeLinkedInPromptApiTest` and `tests/Api/SynchronizeMailboxPromptApiTest` list each prompt with its arguments, get its steps for each argument, refuse a value of `what` out of its list, and check that every tool its text names (`identifier`, and those in kebab-case between backquotes) is served.

## The sign-in of the AIs

Cognito is the authority, but cannot be the authorization server Claude expects by itself: no Client ID Metadata Document nor dynamic registration, no `code_challenge_methods_supported` in its discovery, no `resource` (RFC 8707) in its authorization code. The facade of the API fills those gaps and keeps nothing (`src/SignIn/OAuth`):

- `GET /.well-known/oauth-protected-resource/mcp` (and without `/mcp`, RFC 9728; `SignIn\Controller\ShowProtectedResourceController`, public, out of the contract of the API): `resource` `<api>/mcp` exactly as the member types it in Claude, `authorization_servers` the API alone (Claude reads the first only).
- `GET /.well-known/oauth-authorization-server` (RFC 8414, `SignIn\Controller\ShowAuthorizationServerController`, `SignIn\OAuth\AuthorizationServer`): its endpoints, `response_types_supported: [code]`, `grant_types_supported: [authorization_code, refresh_token]`, `code_challenge_methods_supported: [S256]`, `token_endpoint_auth_methods_supported: [none]`, `client_id_metadata_document_supported: true` (with `none`, the condition of Claude to use it), no `registration_endpoint`.
- `GET /oauth/authorize` (`AuthorizeController`): the client is its Client ID Metadata Document (`OAuth\ClientMetadataDocuments`), an HTTPS URL fetched (its host on no private network, the client `NoPrivateNetworkHttpClient` of Symfony refusing it, 5 s, 5 kB, no redirect followed), its `client_id` equal to its URL, the `redirect_uri` among its `redirect_uris` (`OAuth\ClientMetadata`), a loopback address matched without its port (Claude Code declares `http://localhost/callback` and `http://127.0.0.1/callback`). An invalid client or redirect: 400 `application/problem+json`, its `reason` `unknownClient` (`OAuth\UnknownClientListener`), never a redirect to an address not checked. Then, the redirect checked, what the AI got wrong sends it back with its error: `response_type` other than `code` (`unsupported_response_type`), `code_challenge` S256 missing (`invalid_request`), `resource` other than `<api>/mcp` when given (`invalid_target`). Otherwise a redirect to the sign-in page of Cognito (`OAuth\CognitoSignIn`, `COGNITO_SIGN_IN_URL`) with the client `prospecter-mcp`, a PKCE of the API (`OAuth\Pkce`) and, as `state`, the request sealed for 15 minutes.
- `GET /oauth/callback` (`ComeBackFromCognitoController`): Cognito comes back with its code; a redirect to the AI with its `state` and, as `code`, the request and the code of Cognito sealed (5 minutes); with the `error` of Cognito when the member did not sign in; a `state` the facade did not seal, a 400 leading nowhere.
- `POST /oauth/token` (`IssueTokensController`, `application/x-www-form-urlencoded`): `authorization_code`, the seal opened, the verifier of the AI checked against its challenge, the same client and redirect, then the code of Cognito exchanged with the secret of `prospecter-mcp` (read from Cognito by `UserPool::mcpClientSecret()`, cached) and the verifier of the API at its token endpoint (`OAuth\CognitoTokens`, `COGNITO_OAUTH_URL`), the tokens of Cognito answered as they are; `refresh_token`, passed to Cognito. Every refusal `invalid_grant`, another grant `unsupported_grant_type` (RFC 6749, `OAuth\GrantRefusedListener`). The protocol imposes two exceptions to one intent per endpoint (ADR 0025): `/oauth/token` carries two by its `grant_type`, `/oauth/authorize` and `/oauth/callback` only redirect.
- Nothing kept: the request travels sealed (`OAuth\Seal`, `sodium_crypto_secretbox`, its key `OAUTH_SEAL_KEY` a secret of the API, sealed for one purpose and a while, `OAuth\SealPurpose`), in the `state` given to Cognito then in the code given to the AI; Cognito refusing its code a second time, the code of the facade serves once. No table, no item, nothing in the core.
- Claude web identifies itself by the document Anthropic publishes, its redirect `https://claude.ai/api/mcp/auth_callback`; Claude Code by its own (`https://claude.ai/oauth/claude-code-client-metadata`), on a loopback port of the session. Neither needs anything configured.
- A global sign-out revokes the refresh tokens of every client of the member, their AIs included: the SPA signs out by revoking its own refresh token only (`RevokeToken`), a global sign-out kept for « Se déconnecter partout » in the menu of the account. An access token stays valid until it expires (1 h), as for the SPA (`auth.md`).
